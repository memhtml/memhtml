`@memhtml/head`: the corpus as a value, one version per commit held in persistent `effect` structures. A version is loaded from git, advanced by the paths two commits differ on, and overlaid with a session's pending ops. It is searched by reciprocal-rank fusion over a lexical arm and an optional vector arm, with recency breaking exact ties, and the head gate compares two versions. The design is `docs/design.md` §16.

`HeadVersion` is one version: the read-only view interface `@memhtml/contracts` defines, answered from the version's `Indexes`, plus its commit `sha` and its `parent` version (a pointer, so a caller can walk back). `skippedFiles` lists the candidate files left out because they failed to parse or their blob was missing from the batch read, each a `SkippedFile` with its path and reason, recorded rather than thrown, and `skipped` is their count. `isCandidatePath` decides which tree paths are parsed: a path ending in `.html`, not under a top-level `.memhtml/`, whose file name is not `index.html`. `loadHead` builds the version at a commit from a full tree read: one `ls-tree` and one batched `cat-file` read through `@memhtml/store`'s git service, folding `insertRecord` over the parsed records in tree order. `advanceHead` builds the version at a later commit from its parent. It lists the paths the two trees differ on with one `git diff-tree -r -z --name-only --no-renames`, so a rename contributes both of its paths. It removes the changed candidates absent at the new commit and re-parses the rest unless the blob sha equals the parent record's, and each unchanged path keeps the parent's record object. A changed file that fails to parse leaves the version and joins `skippedFiles`, and a target equal to the parent's `sha` returns the parent itself. `versionFromRecords` builds a version from records already parsed, with no parent and `skipped` 0, by the same `insertRecord` fold.

`recordFrom` turns one file into the flat record type `@memhtml/contracts` defines, and the versions and overlays in this package parse through it. It runs the `@memhtml/html` parser and fails with the parser's own error. To the parsed fields it adds the git blob sha of the text it is given, the article's content hash, the claim's frame key, and the archive flag from `isArchivedPath`, which is true for a path under `archive/`. `blobShaOf` computes the blob sha locally, sha1 over `blob <byteLength>\0` followed by the UTF-8 bytes, because an overlay holds files git has not stored yet. It counts UTF-8 bytes rather than string length, so multibyte content agrees with git.

`Indexes` is the record map and the indexes derived from it, as one value of persistent `effect` maps and sets, so a change to one record builds a new value that shares the untouched structure. Its fields are `records` by path, `byContentHash` (content hash to an active path holding it), `byFrameKey` (frame key to the active paths whose claim shares it), `inbound` (href, as authored, to the paths linking to it), `byEntity` (entity to the paths naming it), and `lexical`. `emptyIndexes` is the empty value, and `insertRecord` and `removeRecord` are its two writers. `insertRecord` replaces any record at the same path, and an archived record enters only `records`, `inbound` and `byEntity`. A content hash goes to the first active record inserted while no path holds it; removing another record that shares it leaves it held, and removing the holder leaves it unmapped even while a twin stays active. `viewOf` puts the read surface over one `Indexes` value and a sha, with `byFrameKey`, `inbound` and `byEntity` returning paths sorted ascending. `indexesOf` returns the indexes behind a view: it reuses them for a view built here and rebuilds them by `insertRecord` over its records otherwise, which is how `searchHead` and `withOverlay` accept a caller's own view.

`LexicalIndex` is the lexical arm's persistent index over active records: per-token postings with each path's term frequency, and per-path token counts with their total, so BM25 reads term frequency and average length at query time without re-tokenizing a body. A record is indexed by its title, claim and body text. `tokenize` lowercases and splits on runs of characters other than Unicode letters, numbers and underscore. It drops empty tokens and the 57 `STOP_WORDS`, a closed list of English function words kept short because a longer one starts dropping content words a memory corpus is searched by.

`withOverlay` is a session's view: the base view with an ordered list of overlay ops (the op type `@memhtml/contracts` defines) applied through `insertRecord` and `removeRecord`. It keeps the base's `sha`, because an overlay has no commit of its own, and fails on the first op that does not parse or resolve. `put` parses a file and inserts it at its path. `archive` removes the old path and inserts the given html, parsed at the destination path, as an archived record. `link` and `unlink` add or cut an edge in the file's head, and `label` and `unlabel` a `memhtml-entity` meta, then re-parse the file; a `link` or `label` naming an edge or entity the file already carries changes nothing. All four fail on a path the view does not hold, `link` and `unlink` also on a rel outside the edge vocabulary, `label` on a malformed entity, and `unlink` and `unlabel` on an edge or entity the file does not carry. `move` re-parses the record's current html, including earlier ops' head edits, at its new path, and fails unless the old path is held and not archived.

`searchHead` ranks the active records of a view and returns `SearchHit` rows. It is synchronous and does not embed, so the caller owns any vectors. A `SearchHeadInput` carries the `query`, a `limit` (default `DEFAULT_LIMIT`, 10), an optional `now`, an optional `admit` predicate, and optionally `vectors`, a `HeadVectors` whose `get` looks a vector up by content hash, with a `queryVector` in the same space. `admit` narrows the records each arm ranks before its cap, while BM25's statistics stay those of all active records. The lexical arm is BM25 (k1 of 1.2, b of 0.75) over the lexical index, counting each distinct query token once, and keeps its best `LEXICAL_ARM_LIMIT` (40). The vector arm runs only when both `vectors` and `queryVector` are set: it scores each admitted active record that has a vector by cosine against the query vector and keeps its best `VECTOR_ARM_LIMIT` (40). Within an arm, records with equal scores share the best rank of their run (1, 1, 3). The arms are fused by reciprocal-rank fusion at k = 60, with `LEXICAL_WEIGHT` and `VECTOR_WEIGHT` both 1.0, and without a vector arm the fold is the lexical arm alone.

Recency only breaks exact ties. Hits are ordered by fused score, then newest first by the record's event time, or its update time when it has none (compared as strings, and clamped to `now` when the input sets it), then by path ascending. A score difference is not overturned and no record is added, so a query no arm matches returns nothing. Each `SearchHit` carries its `path`, fused `score`, `claim`, and `arms`, the `SearchArm` values behind its place: `lexical` and `vector` for the arms that ranked it, and `recency` when its fused score equals another candidate's, which is when recency or path decided its position.

`fillVectors` is the one step in the package that calls an embedder, which keeps `searchHead` free of one. `vectorTextOf` is the text a record embeds: its article text, trimmed and cut to the first `VECTOR_TEXT_MAX_CHARS` (1,800) UTF-16 code units, the same number as `@memhtml/index`'s chunk ceiling. The title is left out because it lives in the file's head, outside what the content hash digests, so a vector that read it could go stale under a key that does not change. A `VectorCache` holds the vectors of one `VectorSpace` (a `modelId` and a `dimension`) by content hash, so an unchanged article keeps its vector across versions, moves and head-only edits; `emptyVectorCache` starts one. `fillVectors` embeds, through a `DocumentEmbedder`, the active records whose content hash the cache lacks. `DocumentEmbedder` is the half of `@memhtml/llm`'s embeddings service a fill needs, typed structurally so this package does not import `@memhtml/llm`. A fill makes at most one `embed` call, with one text per distinct content hash, and skips archived records and records whose trimmed article text is empty. It returns a `FillResult`: the cache with the new vectors added beside the ones it held (vectors for hashes the view no longer holds stay), the `FillCounts`, and `remaining`, the distinct texts a `limit` held back for a later fill. An embedder that answers with the wrong number of vectors or a vector of the wrong width ends the fill as a defect instead of storing anything.

`gateHeads` is the head gate: it asks whether a landed version still finds what its base found, over two versions of the same corpus rather than a fixture. `probesFor` takes the records active in both versions as `HeadGateProbe` rows (a path and a query), so a record the landing adds or archives is not probed. It orders them by the first eight hex digits of sha1 over `<seed>:<path>`, with path breaking ties, and keeps the first `count`, so the sample is a fixed function of the seed and the paths. `probeQueryFor` gives each probe its query from the landed version's record: the title, else the first sentence of the claim, else the claim. `scoreProbes` runs `searchHead` at one version for each probe with a limit of `k` and no vectors, so the gate needs no embedder. `scoreProbes` returns the ranks, the MRR (rounded to four places, 0 with no probes) and two inversion kinds: `fell-out` when the target is not in the top `k`, and `superseded-outranks` when a record named by one of the target's `supersedes` links ranks above the target in the top `k`, or appears there while the target does not.

`gateHeads` scores the same probes at both versions. It passes when the landed MRR reaches the `floor` and the landed version has no more inversions than the base. The `floor` is the base MRR minus the tolerance, clamped at zero and rounded to four places; the tolerance allows for a landing that archives a near-duplicate and so shifts BM25's document frequencies slightly. `HeadGateOptions` overrides `probes`, `k`, `tolerance` and `seed`, which default to `HEAD_GATE_PROBES` (200), `HEAD_GATE_K` (10), `HEAD_GATE_TOLERANCE` (0.02) and `HEAD_GATE_SEED` (1). A `HeadGateReport` carries both MRRs, the `floor`, the landed inversions beside the base's count, and one `HeadGateResult` per probe. `describeHeadGateFailure` renders a report as one line: the probe count, then the MRR shortfall and the inversion growth (with up to five inversions) when they occurred, or `passed`. `HeadGateFailed` wraps a report as a value tagged `HeadGateFailed` whose `reason` is that line, which the CLI maps to `ERR_DISCRIMINATION_FAILED`.
