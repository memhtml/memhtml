`@memhtml/snapshot` holds the two disk caches behind the head. Both are Arrow IPC files, in the file format, under a store's `.memhtml/` directory. A snapshot holds every `MemoryRecord` of one commit, one row per record. A vector cache holds the embeddings of one vector space, one row per content hash. Neither is content: a snapshot can be rebuilt by loading its commit from git, and a vector cache by embedding the articles again. The package depends on `@memhtml/contracts` for `MemoryRecord` and `StorageFailure`, `apache-arrow` for the files, `effect`, and `write-file-atomic` for every write. It does not read git, call a model, or decide when a cache is stale; its callers do. The design is `docs/design.md` §20.

Its one user outside tests is the CLI in `apps/cli`. `apps/cli/src/head-cache.ts` loads a version from its own snapshot, else from an ancestor's snapshot advanced over the changed paths, else from git, and after a commit writes the new sha's snapshot and prunes the directory (`writeHeadSnapshot`, `snapshotAfterCommit`). `apps/cli/src/head-vectors.ts` reads the vector cache for a search, and for `memhtml head embed` fills it and writes it unless an existing cache gained no vector. `apps/cli/src/head-server.ts` writes snapshots and the vector cache from the head server, and `apps/cli/src/v2.ts::headSnapshot` backs `memhtml head snapshot --write` and `--read`. `packages/store/src/layout.ts` names the same two directories.

## Snapshots

A snapshot lives at `.memhtml/snapshots/<sha>.arrow` under the store root: `SNAPSHOTS_DIR` is the directory and `snapshotPathFor` builds the path. Its columns are the fields of `MemoryRecord`, in storage order. `SnapshotColumns` types them, and `LinkColumns` and `FacetColumns` type the `links` and `facets` lists. Only `frameKey`, `eventAt`, `confidence` and `importance` may be null. The schema metadata carries the commit sha under `SHA_METADATA_KEY` and the layout version, `SNAPSHOT_FORMAT`, under `FORMAT_METADATA_KEY`. A file with no format key reads as format `1`, the layout written before the key existed, and the next write of that sha carries the key.

`writeSnapshot` encodes the records, creates the parent directories, and hands the bytes to `write-file-atomic`, which writes a staging file beside the target and renames it into place. While the machine stays up, a reader of that path on a local file system sees the previous file or the whole new one, never part of one. In one thread `write-file-atomic` queues the writes to one path; writes from other threads or processes stage under names of their own, and the last rename wins. The write does not sync to disk. It answers a `SnapshotWriteResult` with the file's `bytes` and `rows`. A failure is a `StorageFailure` whose `operation` is `snapshot.write.encode`, `snapshot.write.mkdir` or `snapshot.write.file`, logged as an error.

`readSnapshot` reads one file and materializes every row as a record, answering `SnapshotContents`: the sha the metadata names, and the records. It does not compare that sha with the file name; `apps/cli/src/head-cache.ts` does, and removes a file that names another sha. Each refusal is a `StorageFailure` naming its step: `snapshot.read.file` for a path it cannot read, `snapshot.read.decode` for bytes that are not an Arrow IPC file or are truncated, `snapshot.read.format` for another format version, `snapshot.read.sha` for metadata with no sha, as an empty file has, `snapshot.read.schema` for columns that differ by name, type, nullability or order, and `snapshot.read.rows` for a null in a column that may not hold one. After decoding, the format is checked before the sha and the columns, because a file of another layout may hold anything under the other keys. `readSnapshotIfPresent` is the same read, except that a file that does not exist answers `null` without a log line; every other refusal is the same `StorageFailure`.

## Vector caches

A vector cache lives at `.memhtml/vectors/<model id>@<dimension>.arrow`, built by `vectorCachePathFor`, with every character of the model id outside `[A-Za-z0-9._-]` replaced by `_` so the name is one path segment. A `StoredVectorSpace` is that model id and dimension, and `StoredVectors` is a space and a map from content hash to `Float32Array`. The file has two columns, the content hash and the vector as a fixed-size list of `Float32`. The metadata carries `VECTOR_CACHE_FORMAT` under `VECTOR_FORMAT_METADATA_KEY`, the model id under `MODEL_ID_METADATA_KEY`, and the dimension under `DIMENSION_METADATA_KEY`, because two model ids can map to one file name.

`writeVectorCache` writes the whole cache in one call, through `write-file-atomic` as `writeSnapshot` does, and answers a `VectorCacheWriteResult`. A vector whose length differs from the space's dimension fails the call with `vectors.write.encode` before any file is touched; the other failures are `vectors.write.mkdir` and `vectors.write.file`. After a write it removes every file beside the cache whose name is the cache file's name, a dot and any suffix, and that is older than `STAGING_ABANDONED_MS`, so no other cache's staging files are touched.

`readVectorCache` opens a file for a given space and answers `ReadVectors`, the stored vectors plus the file's `bytes`, with every vector a view into the one buffer it read. A missing file answers `null`. A file of another format version also answers `null`, with a warning, and stays on disk. A file with no format key reads as format `1`. Every other refusal is a `StorageFailure`: `vectors.read.file`, `vectors.read.decode`, `vectors.read.space` when the metadata names another model id or dimension, or none, `vectors.read.schema` when the columns differ, and `vectors.read.rows` for a null cell. The space and schema refusals are not logged; the callers report them.

## Staging and prune

`write-file-atomic` removes its staging file when a write in the main thread is cut short by `process.exit`, an uncaught error, or a signal the process does not handle itself, such as SIGTERM, and a normal exit waits for the write. SIGKILL leaves one, `<file>.<number>`, beside the target, as does a worker thread's write when the worker is terminated or the process exits under it. `sweepStaging` removes the files in one directory whose names a predicate accepts and whose modification time is more than `STAGING_ABANDONED_MS`, one hour, before now, and answers the names it removed. It never fails: a directory it cannot read or a file it cannot remove is a warning and the empty answer, even when it removed other files first, a file it cannot stat is passed over, and a missing directory is the empty list.

`listSnapshots` lists every `<sha>.arrow` under one root's snapshot directory whose sha is 40 lowercase hexadecimal characters, as a `SnapshotEntry`, newest first by modification time and then by sha. Staging files and other names are not listed, and a missing directory is the empty list. A file it cannot stat fails the call with `snapshot.list.stat`. `pruneSnapshots` keeps the newest `keep` snapshots, `SNAPSHOTS_KEPT` (4) by default and never fewer than zero, removes the rest, and answers their shas, newest first. A file already gone when it is removed counts as removed. It then sweeps the directory's abandoned snapshot staging files, which are not in the answer. Its failures are `snapshot.list`, `snapshot.list.stat` and `snapshot.prune.unlink`, and a failed removal stops the call before the sweep.

## Modules

The package publishes one import path, `@memhtml/snapshot`. Its `index.ts` re-exports every export of `snapshot.ts`, `vectors.ts`, `staging.ts` and `prune.ts` except `bufferOf`, so the reference on this page is that set. `bufferOf` in `staging.ts` is internal.

| Module        | What it holds                                                                                                                                                                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot.ts` | `SHA_METADATA_KEY`, `FORMAT_METADATA_KEY`, `SNAPSHOT_FORMAT`, `LinkColumns`, `FacetColumns`, `SnapshotColumns`, `SNAPSHOTS_DIR`, `snapshotPathFor`, `SnapshotWriteResult`, `writeSnapshot`, `SnapshotContents`, `readSnapshot` and `readSnapshotIfPresent`.           |
| `vectors.ts`  | `VECTOR_FORMAT_METADATA_KEY`, `VECTOR_CACHE_FORMAT`, `MODEL_ID_METADATA_KEY`, `DIMENSION_METADATA_KEY`, `VECTORS_DIR`, `StoredVectorSpace`, `StoredVectors`, `vectorCachePathFor`, `VectorCacheWriteResult`, `writeVectorCache`, `ReadVectors` and `readVectorCache`. |
| `staging.ts`  | `STAGING_ABANDONED_MS` and `sweepStaging`, which `writeVectorCache` and `pruneSnapshots` call, plus `bufferOf`, which is not exported from `@memhtml/snapshot`.                                                                                                       |
| `prune.ts`    | `SNAPSHOTS_KEPT`, `SnapshotEntry`, `listSnapshots` and `pruneSnapshots`.                                                                                                                                                                                              |
