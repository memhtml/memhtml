`@memhtml/html` is the memory file format: parse, serialize, hash, fence-language detection, the surgical head editors, the template that writes a new file, and the closed vocabulary all of them read. The format is semantic HTML5 over that vocabulary and this package is its only implementation, so a memory file stays a document a browser renders with no server, and the index stays derivable from the tree alone. Every element in the vocabulary earns its place by carrying indexer semantics, which is why the parse output is named for what the indexer stores rather than for the markup it came from: `gist` is the one `<mark>`, `eventAt` is the first `<time>`, `facets` are the `<dl>` pairs. The package sits on `parse5`, `effect`, a pinned `highlight.js`, and `@memhtml/contracts` for the closed edge, type and error vocabularies.

`vocabulary.ts` is the bottom of the stack and holds no logic, because the vocabulary IS the policy: there is no sanitizer library here and no allow/deny engine, only data. Both metadata planes use the same hyphenated prefix (`META_PREFIX`, `LINK_REL_PREFIX`) because HTML5 metadata names are a flat token space and a `rel` token cannot hold a colon at all. `REQUIRED_META` is the four facts no pure function can invent, a type, a status, and the two write stamps; `memhtml-confidence`, `memhtml-importance` and `memhtml-author` are deliberately absent because the `files` table documents a default for each, so a hand-authored file missing them is completed rather than refused. `META_ORDER` is the emit order and a diff-stability contract: a new scalar goes at the end of the scalar block and a new repeatable at the end of the repeatable block, so two agents stamping different keys leave each other's lines in place. `REPEATABLE_META` names the three keys that may appear more than once, one element per value so correcting one tag is a one-line diff, and `isMemoryMetaName` and `isRepeatableMeta` are the predicates over both lists. The element tables split by role: `DOCUMENT_ELEMENTS` is the skeleton that carries no indexer semantics, `ARTICLE_ELEMENTS` is one entry per row of the format's element table (with `tr` added, because a `<table>` cannot hold a cell without a row), `PERSON_ELEMENTS` is the `<address>` a person file adds, `FIGURE_SCOPED_ELEMENTS` is `<div>` and `<span>` permitted only inside a `<figure>` where a pasted sample carries its own containers, and `KNOWN_ELEMENTS` is their union. The rest are serialization and scoping facts the writer and the hash need: `VOID_ELEMENTS`, `GIST_EXCLUDED_ELEMENTS` (a command line is body text and searchable, and it is not the claim), `FORBIDDEN_ELEMENTS` and `FORBIDDEN_ATTRIBUTES`.

`tree.ts` is parse5 navigation narrowed to what the format needs, pure, total, and ignorant of the vocabulary. Source locations are always on, because the head editors splice by byte offset and a second parse to obtain them would let two views of the same bytes disagree. `parseArticleFragment` parses article inner HTML in `<article>` context on purpose: fragment parsing without a context element runs in `<template>` content, where table-scoped elements are foster-parented out and their text would vanish from the digest, so parsing in the element the markup came from is what makes `contentHash` agree on a doc and on the whole file. The walks are iterative rather than recursive so a pathologically deep hand-authored file cannot overflow the stack. `markup.ts` is the writer, and it exists because parse5's own serializer is unusable here for two reasons. The costlier one is `<pre>`: the parser swallows one newline after the start tag and parse5 does not re-emit it, so a file loses one newline on every write, and `<pre>` whitespace is inside the hash scope verbatim, so that drift would move a memory's dedup key on a pass that edited nothing. The second is attribute order, which parse5 preserves, leaving two files differing only in attribute order as different bytes forever; sorting by name canonicalizes them. `escapeText` writes U+00A0 as `&nbsp;` because an invisible character in a claim is a trap, and `escapeAttribute` turns line breaks into character references so an emitted `<meta>` or `<link>` is always one source line, which is what the line-splicing editors depend on.

`hash.ts` owns the one value in the system that must be invariant under head edits. The content hash is `sha256` over the whitespace-normalized text content of `<article>`, except inside `<pre>` where whitespace passes through byte for byte, so meta and `<link>` edits are outside the scope by construction and confidence decay, access bookkeeping and the sleep phases' own stamping never look like content changes. Without that invariance a corpus-wide decay pass would present the whole corpus as new content and dedup would collapse. Only ASCII whitespace collapses; U+00A0 is content, because a non-breaking space inside a claim is a typographic decision worth preserving. A block element contributes a collapsible space at each edge, so the digest is a function of the article's words and not of its indentation, and the outer trim applies only to a leading or trailing collapsible segment, since trimming the whole result would let `<pre>  a</pre>` and `<pre>a</pre>` hash identically. `canonicalText` takes `CanonicalTextOptions`, whose `excludeCode` omits `<pre>` and `<code>` per the gist rule, `canonicalArticleText` is the same fold with code kept, and `contentHash` accepts a parsed doc, an article node, a `HashableArticle`, or raw HTML, locating `<article>` first so head content never reaches the digest and hashing a string with no article as article-inner-HTML rather than failing, because refusing malformed input is `parseMemory`'s job and not the digest's. `HASH_ALGORITHM` is the prefix that makes a stored digest self-describing and `isContentHash` recognizes the `sha256:<64 hex>` form.

`constraints.ts` is the six format constraints as pure predicates over a parsed document. Constraints 1 through 5 are violations and the file is not a memory; constraint 6 is a warning, because an element outside the vocabulary still indexes and the format has to degrade gracefully on a file a human hand-wrote in a hurry. Nothing here throws and nothing repairs: a checker that silently fixed a violation would make `memhtml doctor` report a clean corpus that the next hand-edit breaks again. `isValidDatetime` admits exactly two forms, an ISO date and a canonical UTC instant, and is narrower than HTML's own `datetime` grammar because `files.event_at`, `files.due_at` and `files.valid_until` are compared and ordered as raw strings, so every admitted value has to sort lexicographically as it sorts chronologically; a space separator, a non-UTC offset, or optional seconds each break that, and range is checked too so `2026-13-45` is refused rather than stored as an unsortable date. `isRootRelativeHref` requires the document-reference form, repo-root-relative with a leading slash and no scheme, host or `..` segment, since a relative href breaks on the first `git mv` of the source file and a protocol-relative one silently leaves the repo. The `<mark>` rules are the format's center: exactly one, non-empty, leading the article's first `<p>` or `<li>`, and never inside an `<aside>` or `<details>`, so a recall line cannot quote a caveat or something the author chose to hide. Emptiness is tested with the real gist rule (`canonicalText` with `excludeCode`, then trimmed) rather than a convenient approximation, because `parse.ts` derives `gist` from exactly that text, so `<mark><code>drain --vip</code></mark>` indexes with no gist and is refused. `checkDocument` collects rather than short-circuits, so one parse tells an author everything wrong with the file, and returns a `CheckResult` of violations and warnings in constraint order then document order, with warnings deduplicated by element name so forty stray `<div>`s produce one actionable line. `VIOLATION_SEPARATOR` is how that list is joined into the single string `InvalidMemory.reason` carries.

`parse.ts` implements the extraction table one element at a time, and the interesting part is what it refuses versus what it drops. A malformed optional meta is dropped and left for `memhtml doctor`: `memhtml-confidence="high"` means the file stated no confidence and the `files` default applies, and a blank value is malformed rather than zero, since `Number("")` is `0` and a blank confidence must not index as `0.00`. The datetime metas and the task metas are refusals instead, because a drop is only safe where the `files` table owns a default and an instant has none: dropping an unsortable `memhtml-valid-until` WIDENS the window to always-valid, so the file would answer an as-of query for instants it said the fact was already dead, and a `task` with no `memhtml-task-status` has no lifecycle position at all, so it would be invisible to the surface that exists to show it. `parseMemory` fails with `InvalidMemory` and no partial doc, and `checkMemory` is the total variant that returns the structured violation and warning lists without building one. `document.ts` holds the shapes, as Effect schemas paired with the interfaces they decode to, and they live here rather than in `@memhtml/contracts` because they are format types: the extraction fields exist only because the HTML has those elements. `MemoryMetas` states each field's coordinate space on the field, and an absent value means the file did not state it, with no default substituted, so a hand-authored omission stays distinguishable from a deliberate assertion. `ArticleExtractions` is what the indexer reads out of `<article>`, with `html` a serialization fixed point, `bodyText` the FTS and embedding input including asides, details bodies, captions and `<pre>`, `gist` the one span nothing derives, `eventAt` the world time the recency arm coalesces with the write stamp, and the document-order lists (`facets`, `citations`, `definedTerms`, `summaryTexts`, `asideTexts`, `captions`, `codeLangs`, `abbreviations`) each feeding their own table or entity promotion. `MemoryLink` carries an unprefixed rel from the closed edge vocabulary with the href as the file spells it, `Facet` pairs a `<dt>` with each of its `<dd>`s and carries a `numericValue` only when a `<data value>` parses as a finite number, deliberately unitless because the unit lives in the human phrasing, and `Citation` is a `<cite>` or a `<q>` with its optional source URI.

`serialize.ts` is the inverse: `parseMemory(serializeMemory(doc))` yields the doc again, which is the property that lets sleep read, adjust and write a file back without touching content it did not mean to touch. The output is deterministic, one `<meta>` per line in `META_ORDER` with no head indentation, so stamping `memhtml-updated` produces a one-line git diff a human actually reviews, and `article.html` is re-parsed and re-serialized rather than interpolated so a hand-assembled doc still gets the canonical fixed-point markup. `metaPairs` is the ordered `[name, content]` expansion, repeatable keys one pair per value, confidence rendered to two decimals and every other number as an integer. `editors.ts` is the alternative to that round trip for a bookkeeping pass: byte-level splices that change exactly one line and provably do not touch the article. The sleep phases stamp `memhtml-updated`, decay `memhtml-confidence`, bump `memhtml-reprieves` and set `memhtml-needs-revision` on files they otherwise leave alone, and re-serializing the whole document for that would make the pass look like a content change in `git diff` and risk moving the dedup key. Splicing by source offset keeps the hash invariant by construction, so `contentHash(setMeta(html, name, value))` equals `contentHash(html)` for every name. `setMeta` replaces the first meta of a name or inserts a line in `META_ORDER` position and refuses an unknown name by returning the input unchanged, `addMeta` appends another value of a repeatable name and is a no-op on a value already present so a re-run of a phase cannot grow the head, `addLink` is idempotent on the `(rel, href)` pair because the conflict phase promotes the same corroborated edge on each run and a duplicated `<link>` would become a duplicated `edges` row, `removeMeta` and `removeLink` cut whole lines (omitting `href` drops every link of that rel), and `readMeta` and `readLinks` are the deliberately tolerant read halves: the document is parsed and nothing is validated, so a caller holding raw bytes can ask what a file points at without the file having to be a well-formed memory.

`fences.ts` owns the fenced-code grammar and only the grammar: what opens a fence, what closes it, and what language its info string names. There is one copy because the template renders a block and the write doors split prose into paragraphs, and two answers to "is this line a fence?" would let the splitter keep a block intact that the template then fails to recognize. Backtick fences only, per CommonMark: three or more open, a run at least as long closes, and the info string may hold no backtick; tilde fences are deliberately absent because agents write backticks. `LANG_TOKEN` is the language-token grammar, wide enough for `ts`, `c++`, `c#` and `objective-c` and closed to whitespace and markup characters, so a `data-lang` value is always safe in view-source and safe to promote to a `lang:` entity. `fenceOpeningOf` and `closesFence` are the line-level predicates, and `fencedBlockOf` returns a `FencedBlock` only when the whole paragraph is the fence: prose sharing a paragraph with a fence is not a fence, and an unterminated fence is `undefined`, because rendering either as code would commit markup the author may not have finished while escaping it as text keeps the file saying what the author typed.

`detect.ts` is a port of a measured detector, not a fresh design, because an unlabeled fence carries no language and wrong metadata costs more than none. A private evaluation corpus swept two candidates, `flourite` and highlight.js `highlightAuto`, over 332 real fences and file slices and picked the operating point where measured precision first reaches a 95% floor: highlight.js won at threshold 0.28685957116771854 with precision 95.18% at 25.0% coverage, where `flourite` reached 100% precision at only 3.0% coverage, abstaining exactly where this one stamps. `DEPLOY_THRESHOLD` is 0.30, a conservative rounding up of that point, safe because confidence is monotone in evidence: re-measured on the same corpus it stamped 81 snippets, 77 correctly, for 95.06% precision at 24.4% coverage, and both numbers are recorded because the measured one is the evidence and the deployed one is the decision. `detect` returns a `Detection` with the threshold not yet applied, scoring `1 - exp(-(top - runnerUp) / lines)`, the per-line evidence margin between the winning grammar and its closest real competitor, where a runner-up normalizing to the same canonical token is not disagreement and so charges no penalty, and where hljs runs its full grammar set deliberately: restricting it to the twelve-name vocabulary measured 0.9% coverage against 25%, because with the true language's grammar absent a runner-up wins unopposed and wins confidently. `detectLang` applies both independent gates, in-vocabulary and at or above the threshold, since a confident detection of a language outside `CANONICAL_LANGS` is still nothing, and the corpus has hljs naming `smali` at 0.86 and `autohotkey` at 0.55 for snippets that are really bash and TypeScript. `CANONICAL_LANGS` is one lowercase token per language because `data-lang` promotes to a `lang:` entity by exact string match, and `normalizeLang` folds the aliases seen in detector output, info strings and file extensions (highlight.js names its HTML grammar "xml", ships no TOML grammar, and SQL dialects collapse because a dialect distinction is noise at entity granularity). Three operational decisions come with the port. highlight.js is pinned exactly, no caret, because relevance scores are grammar-dependent and a bump silently moves every confidence and therefore which fences get stamped; measured against 11.12.0, one snippet fell from 0.5406 to 0.1993 and stopped stamping `toml`, so a bump is a deliberate decision that re-runs the eval and re-derives the threshold. The library loads lazily on the first detection, because eagerly imported its 192 grammars cost roughly 100ms and 12MB in every process that touches the format layer, including the read path, which detects nothing. Fences longer than 4096 characters abstain without running hljs at all, since `highlightAuto` is super-linear in input size (5KB is about 450ms and 100KB about 122s of blocking CPU on the pinned build) and the MCP server is one single-threaded process, so an uncapped detector would let one large unlabeled fence wedge every other request. Detection is also write-time only: the stamp goes into the file, which is the system of record, and rebuild reads `data-lang` back through `parse.ts` and never re-detects, so a dropped and rebuilt index stays a pure function of the tree instead of a function of the installed hljs version. Author strings are untouched throughout, since this vocabulary gates detector output alone.

`template.ts` is what the write path calls instead of the serializer, because an agent supplies a title, a claim and prose, and something has to turn that into the `<mark>`-led first paragraph the format requires: an agent hand-authoring that placement would violate constraint 1 regularly, and a template that places it always places it correctly. `NewMemoryInput` mirrors the write tool's parameters, with `claim` required because a memory with no claim has nothing to disclose at Tier 1, `body` one string per paragraph, and `articleHtml` the escape hatch for a correction carrying its own `<dl>` or `<figure>`, where the caller then owns constraint 1. `articleHtmlFor` joins the first body paragraph onto the claim's own paragraph as its tail, drops empty paragraphs, and renders a body paragraph that is a fenced block as `<figure><pre><code data-lang>` rather than a `<p>`, never joined onto the claim, so the claim still leads the article and code stays out of the sentence; the language rides on `data-lang` because `class` is a constraint-3 violation and `lang` is a human-language attribute, and the info string wins outright, so `detectLang` runs only on an unlabeled fence and no detector opinion overrides what a human wrote. `DEFAULT_TASK_STATUS` is `todo`, defaulted rather than required of the caller because `parseMemory` refuses a task with no `memhtml-task-status` and it is stamped only for a task, since a non-task carrying one is a file git holds and the indexer skips. `newMemoryDoc` builds the doc with `memhtml-content-hash` already stamped from the article the template just built, so the file reaching disk is self-consistent and the indexer's own recomputation agrees with it on the first read, and `renderTemplate` is the one function the write path calls for bytes.

The package publishes one import path, `@memhtml/html`, which re-exports the eleven modules below, so the reference on this page is the whole exported surface. `tree.ts` is internal: it reaches consumers only as the parse5 node types the other modules accept and return.
