`@memhtml/store` is the v1 write path: a store service over one git working tree in which every operation that changes a record is one commit. Beside the service it holds the git runner the service stands on, the repository layout and the one function that scaffolds it, pure parsers for git's output, and the lock that keeps two writers of one checkout apart. It depends on `@memhtml/contracts` for the path rules, the edge vocabulary, the typed failures and the lock's rules, on `@memhtml/html` to render, check and edit a record, and on `effect` and `proper-lockfile`. It opens no database and calls no model. The one question a write asks the SQLite index and the one notice it gives the state database arrive as `StoreHooks`.

Its main user is the CLI in `apps/cli`. `apps/cli/src/api-layer.ts` builds the `Git` service over the configured root and the `Store` over that, with `dedupeLookup` asking the SQLite index for an active file with the same content hash and `onMove` renaming the path in `state.access`. `apps/cli/src/operations.ts` calls `writeMemory`, `writeMemories`, `readMemory`, `correctMemory`, `linkMemories` and `archiveMemory`, and uses `exclusive` for a task status change. `apps/cli/src/run.ts` calls `initRepo` for `memhtml init`. `apps/cli/src/doctor.ts`, `apps/cli/src/state.ts` and `apps/cli/src/publish.ts` stage and commit files of their own under `withCheckoutLock`. The session commands and the head server use `makeGit`, `isoSecond` and `parseNulPathList`, and never the `Store`. `apps/mcp/src/resources.ts` reads blobs through the store's `git`. Outside the apps, `packages/eval/src/fixture.ts` uses `initRepo` and `makeGit`, and `packages/head/src/version.ts` uses `GitShape`, `TreeEntry` and `parseNulPathList`. `supersedeMemories`, `mergeBranch` and `requireCleanTree` have no caller outside this package's tests.

## The store service

`makeStore` takes a `GitShape` and optional `StoreHooks` and returns a `StoreShape`; `Store` is the service tag for one. Each failure is a `StoreError`: `GitFailure`, `StorageFailure`, `InvalidMemory`, `PathNotFound`, `WriteConflict` or `DirtyTree`. `readMemory`, `dirtyPaths` and `requireCleanTree` read and take no lock. `dirtyPaths` lists every path `git status` reports that is not ignored, and `requireCleanTree` fails with `DirtyTree` when that list is not empty.

`writeMemory` takes a `WriteInput` and runs four checks before it touches disk. With `strictPath` set, an explicit `path` that is not a usable memory path is refused with `InvalidMemory`. The record is rendered and checked, and bytes the format rejects are `InvalidMemory`. The `dedupeLookup` hook is asked about the content hash, and when it answers a path the call ends there with `deduped: true`, that path, and no commit. Then a free path is chosen. An explicit usable path is taken as given, or refused with `WriteConflict` when a file is there. With no explicit path the placement rule's path is used, with `-2`, `-3` and so on until no file holds it. An unusable path without `strictPath` is placed by the rule, so the `WriteResult` can name a path the caller did not. The call then writes the file, stages it and commits `memhtml(write): <title>`, with `Memhtml-Session` and `Memhtml-Prompt` trailers when the input carries a session or prompt id.

`writeMemories` is many writes in one commit. It validates the inputs in order, with the same four checks, each against the inputs accepted before it. Two inputs with one title get two paths. The second of two inputs with one article is reported `deduped` at the first one's path. Two inputs naming one explicit path leave the second with `WriteConflict`. A `task` input is never treated as a duplicate in a batch. By default the first refused input ends the call with nothing written: that input carries its error and every other one is `skipped`. With `continueOnError` a refused input is passed over instead. The inputs that passed are then written, staged and committed together as `memhtml(batch): <n> memories`, or the one title when one file was written. A refused input is a `BatchOpResult` in the answer, never a failure of the call.

`correctMemory` replaces a record in one commit. It refuses a target that is not a usable memory path or is already under `archive/` (`InvalidMemory`) and a target with no file (`PathNotFound`). It moves the target with `git mv` to its archive slot, `archive/<year>/<original path>`, or `archive/<year>.2/` and up when that slot holds a file, and stamps the moved file's head with `memhtml-status` `archived`, `memhtml-archived`, `memhtml-updated`, `memhtml-superseded-by` and, unless it already states an earlier one, `memhtml-valid-until`. The new record gets a `supersedes` link to the archive path and a `memhtml-valid-from` when it states none. The target's own path may be named as the new record's path; any other occupied path is `WriteConflict`. `archiveMemory` is the move and the first three stamps alone, committed with the path and the reason as the subject.

`supersedeMemories` takes winner and loser pairs of files already in the tree. It reads every file before it stages anything, so a missing path fails the call with nothing changed. It archives each loser as a correction archives its target, with `memhtml-superseded-by` naming the winner, adds a `supersedes` link to each winner, and commits all pairs as one `memhtml(consolidate)` commit. An empty list answers a null `commitSha` and runs no git command.

`linkMemories` adds one edge to the source file's head and commits it. Adding an edge the file already carries changes nothing and answers a null `commitSha`. It refuses a link from a path to itself, a rel of the memory class when either end is a `task`, and a rel of the task class unless both ends are tasks, each with `InvalidMemory`, and those two class checks read both files. `mergeBranch` runs a merge of another branch into the checked-out one. On a content conflict it reads the two blob ids from git's index, aborts the merge, and fails with `WriteConflict` naming the path and both ids.

## Failure and interruption

Every check above runs before the first byte is written, so a refusal leaves the working tree and git's index as they were. From the first write on, an operation keeps a journal of what each path it touches held before. When a later step fails, or the caller interrupts the call, the operation unstages those paths with `git reset`, removes the files it created, and rewrites the bytes it replaced or moved away. The call then fails with the original failure, or ends interrupted. For example, when a `pre-commit` hook refuses the commit, each of the six operations that change a record leaves the branch and the files as they were before the call. Git's index is as it was too, except that a change the caller had staged on a path the operation touched comes back unstaged. Paths the operation did not touch are left alone, staged or not.

That guarantee belongs to one call in a live process. The cleanup runs inside the process that made the call, so a process that is killed part way runs none, and the tree stays as it was left until someone repairs it. A cleanup step that itself fails is logged, and the call still fails with the original failure. The `onMove` hook is called after a file is moved and staged and before the commit, and it is not called again when the operation is undone. A commit takes the whole of git's shared index, so a file some other tool staged in the checkout goes into the next store commit.

## One writer at a time

Every writing method of a `StoreShape` runs inside its `exclusive`, which takes a permit and then a lock. The permit is held by that one store value, so its own concurrent calls run one after another. The lock is the checkout lock, `withCheckoutLock`: a `proper-lockfile` lock directory, `.memhtml/checkout.lock` under the root, taken across processes and removed on release. Two store values over one root, in one process or two, exclude each other through it, and so does a session commit, because `@memhtml/session` computes the same path. A writer that finds the lock held waits, for the time `CHECKOUT_LOCK_WAIT_MS` in `@memhtml/contracts` sets, and then fails with `StorageFailure` `checkout.locked` having written nothing. A holder refreshes the lock while it holds it, and the next writer reclaims a lock that has gone `CHECKOUT_LOCK_STALE_MS` without a refresh. The lock is reentrant within the effect that holds it and the fibers that effect forks. The permit is not: an effect passed to `exclusive` must not call a writing method of the same store.

`GitShape.commit` takes the checkout lock itself, so a caller that commits without `exclusive` is still excluded during the commit, but not between its `add` and its commit. A caller that stages and commits through `store.git` wraps both in `exclusive` or `withCheckoutLock`, as the CLI's task status change, `publish`, `state export` and `doctor --fix` do. `checkoutLockTarget` names the lock's target for a root.

## The layout and `initRepo`

`layout.ts` names each path under `.memhtml/` (`MEMHTML_DIR`) as a constant. `GITIGNORE`, `GITATTRIBUTES` and `README` are the three root files a new store gets, and `SCAFFOLD_DIRS` the directories, each held by an empty `.gitkeep`. `initRepo` creates the root and runs `git init -b main` only when the root is not inside a git work tree; an existing repository keeps the branch it has. On every run it sets `MERGE_OURS_DRIVER` and `MERGE_DIRECTORY_RENAMES` in the clone's config and writes each scaffold file that is absent. It then stages the scaffold and commits `memhtml(init)` when git's index differs from `HEAD`. So a second run writes no scaffold file and commits nothing, a run after one that failed at the commit finishes it, and a scaffold file edited since is kept and committed as edited. `InitResult` reports the files written and the head commit. `ensureConfig` sets one config value unless the clone already holds that value.

## The git runner and the parsers

`makeGit` returns a `GitShape` for one root, and `layerGit` provides it as the `Git` service. Every method runs `git -C <root>` as a child process with terminal prompts off, optional locks off, the C locale, and the variables that select a repository from the environment removed. A non-zero exit is a `GitFailure` carrying a `command` label and the exit code, never the arguments. Exits that are answers are values instead, for example no commit yet, a ref that does not resolve, a merge conflict, a commit that is not an ancestor. `commit` with nothing staged answers a `CommitResult` with a null `sha` and `empty: true`. `add` passes each path through `literalPathspecs`, so git matches it literally, and fails on an empty path before git runs. An interrupted call waits for its child to exit.

`plumbing.ts` holds the pure parsers for the formats those methods request (`parseLsTree`, `parseDiffNameStatus`, `parseStatusPorcelainV2`, `parseCatFileBatch`, `parseNulPathList`, `parseTrailerLog`) and the commit message rules. `commitSubject` builds `memhtml(<operation>): <subject>`, with the subject flattened to one line and cut to `COMMIT_SUBJECT_MAX` characters, and `(untitled)` for an empty subject. `provenanceTrailers` flattens a session id and a prompt id to one line each and leaves out an empty one.

## Beside `@memhtml/session`

`@memhtml/session` is the v2 write path and never imports this package. A store operation stages into the checkout's shared git index and commits there at once. A session keeps a log of operations and lands it later as one commit, as that package's page describes. The two meet at three points. Both take the same checkout lock. Both use the `memhtml(<scope>): <summary>` subject shape and the `Memhtml-Session` trailer key. And each enforces rules the other does not: the endpoint class check of `linkMemories` is not applied to a session's `link`, a session archive does not call `onMove`, and the write bar a session commit validates against is not applied here.

## `@memhtml/store/testing`

The second import path is for tests, in this package and in the packages and apps that depend on it, and is not part of the reference below. `makeFixtureRepo` makes a new directory under the OS temp directory and, unless `init` is false, a real scaffolded repository in it with a fixture git identity, signing off and git's background maintenance off. It answers a `FixtureRepo` with its `git`, its `store` and a `cleanup`. `configureIdentity` sets the same identity on a repository made another way. `mapDedupeLookup` and `recordingMoveCallback` are the two hooks over a map and an array, and `writeInput` is a minimal `WriteInput`. `throwawayRoot`, `throwawayTestEnv`, `assertThrowawayRootUntouched` and `throwawayRootGlobalSetup` pin a test run's `MEMHTML_ROOT` to a per-process path that nothing creates, and fail the run when a test did create it.
