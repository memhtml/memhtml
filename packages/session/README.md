`@memhtml/session` is a session's overlay log and the mechanical path that commits it. A session is a base commit, the ref its commit will land on, and an ordered list of operations, kept in one JSON file per id under `.memhtml/sessions/`. The package depends on `@memhtml/contracts`, `@memhtml/domain` and `@memhtml/html`, plus `effect`, `proper-lockfile` and `write-file-atomic`. It never imports `@memhtml/store`. It runs `git` itself, because the store's git service strips `GIT_INDEX_FILE` and a commit stages into an index file of its own. The CLI in `apps/cli` uses most of the package, and `@memhtml/curator` imports `BATCH_CAP` and the `Violation` type. The design is `docs/design.md` §17.

`Session` is a session's state in memory, plus the store `root`, which is not saved, so a log is always found by root and id. `startSession` takes a `SessionBase` and reads only its `sha`. It checks that the sha names a commit and writes an empty log. Unless `force` is set, it refuses with `session.exists` an id that already has a log, so a retried start cannot replace work in progress. The new session's `ref` is `DEFAULT_REF`, `refs/heads/main`, unless the caller passes one: it does not follow the branch the checkout has open. `resumeSession` reopens a log. `decodeLog` turns a log's text into session state and fails on text that is not JSON, not a log, or another id's log. A log's ops decode through `OverlayOpSchema`, which the head server's wire protocol uses too. An id must match `SESSION_ID`, one path segment, so a log cannot leave `SESSIONS_DIR`. `isSessionId` tests an id and `sessionStateFile` names its log.

Every write to a log runs inside `withSessionLock`, which holds an exclusive `proper-lockfile` lock directory, `<id>.lock`, beside the log. It covers one id in one checkout, across processes. A second writer does not wait. It fails at once with `session.locked`, because the right answer to a command sent twice is a refusal, not a second commit. The holder refreshes the lock's mtime, and a lock with no refresh for `SESSION_LOCK_STALE_MS` (30 s) can be taken by the next writer of the same id. `SessionLockOptions` lets a test shorten the refresh.

A lock alone would still lose an update, because a caller reads the log, works for a while, and writes after. So `appendOps`, `saveSession`, `replaceOps` and `commitSession` read the log again under the lock and go ahead only when it still holds the ops the caller read. Otherwise each fails with `LOG_MOVED` (`session.moved`) and writes nothing. Only the ops are compared, not the base. `appendOps` adds ops and returns the session to keep using. `rebaseSession` is pure: it moves `baseSha` to the version it is given and writes nothing, and `saveSession` persists the result. `replaceOps` swaps the whole list, which `session commit --drop-refused` does to take refused ops out.

`pending` is a commit that `commitSession` built and wrote to the log before it touched the checkout. A process that dies before clearing it leaves that record, and the next `commitSession` or `appendOps` on that id settles it under the checkout lock. If the commit is reachable from the ref, it landed, and the session moves onto it and drops the ops it carried. If not, the settle tries to undo any checkout update the dead call made, and the ops stay. `appendOps` settles `pending` before it adds anything, so new ops never sit beside a commit that may have landed. `replaceOps` refuses a log that carries one, with a failure that starts with `SESSION_PENDING`.

`commitSession` lands the whole log as one commit and calls no model. It holds the session lock for the whole call. It settles `pending` first, and answers `committed` with `recovered` set when that commit had landed. It runs `validateOps` against the `head` the caller passes and answers `refused` on any violation. It answers `rebase-needed` when the ref names a commit other than that head's `sha`, because a duplicate or a frame-key rival can arrive on paths the session never touched. It applies the ops over the head and builds the blobs, tree and commit through a temporary index file under the OS temp directory, so building the commit never touches the shared index. Then it writes the commit to the log as `pending`, lands it with `landOnRef`, and saves the log with the commit as its base and no ops. `CommitOutcome` is the answer: `committed`, `rebase-needed`, `refused` with each `Violation`, or `worktree-dirty`.

While `commitSession` applies the ops, a put gets a `contradicts` edge to each other active record in the head whose claim shares its frame key, and both stay live. A rival that agrees with the put, that the put supersedes, or that the batch archives gets no edge. That pair comes back under `restatements` with a `RestatementReason`, one of `RESTATEMENT_REASONS`. `commitSubject` builds the one-line subject `memhtml(<scope>): <summary>`, with the summary capped and never empty. `commitMessage` adds a `Memhtml-Session: <id>` trailer, which is how a session commit names its session. `archiveBody` stamps `memhtml-status archived` and a `memhtml-archived` instant into the HTML head of a record, so the article and its content hash do not change.

`landOnRef` moves the checkout and then the ref as one section under `withCheckoutLock`. That lock is the directory `.memhtml/checkout.lock` in one checkout, and `@memhtml/store` computes the same path for its writes, so a session commit and a v1 write in that checkout take the same lock. A waiter retries for up to 15 s by default and then fails with `checkout.locked`. The lock is reentrant within one fiber, and once it is held the section cannot be interrupted. `checkoutLockTarget` names the lock's target, `.memhtml/checkout` under a root.

Inside the section, the ref must still name `expected`, or the answer is `raced` and nothing moves. When `HEAD` is the ref, uncommitted state at a path the commit changes is `worktree-dirty`; with those paths clean, a two-tree `read-tree -m -u` moves the shared index and working tree to the new commit and keeps uncommitted edits at other paths. Last, `update-ref` with the expected old value is a compare-and-swap that git enforces on that one ref, even against a writer that skips the checkout lock. When the swap is lost and `HEAD` is the ref, the reverse `read-tree` runs to put the checkout back. The checkout moves first because the other order would leave `HEAD` ahead of the index on a failure, and git would show the session's files as staged deletions. `Landing` is `landed`, `raced` or `worktree-dirty`, a lost swap is `raced` too, and `commitSession` answers `raced` with `rebase-needed`.

`validateOps` is a pure function of a `HeadView` and a list of ops that returns a list of `Violation` values and does no I/O. The CLI calls it before `session put` and `session exec` append and in its curation commands, so they judge ops with the function the commit runs. `ValidateOptions` carries the `scope`, the store's `writeBar`, and a `batchCap` that defaults to `BATCH_CAP`, 200 ops. A `CommitScope` is `session` or `curate`, and it is the caller's to pass: `validateOps` and `commitSession` default to `session` and do not read it from the ref. `isReservedPath` says which paths a scope may not write: a path under `.memhtml/`, `memhtml.config.json`, any `index.html` or `sitemap.xml`, and outside `curate`, `areas/arcs/` and `resources/people/`. `touchedPaths` lists the paths one op reads or writes.

`writeBarReasons` judges one new record against the store's write bar: a type the store refuses, and, when the bar requires an anchor, a record that has no entity and is not under `projects/`. `UNANCHORED_REASON` is the reason that rule gives. The library default refuses nothing, so a caller judging a real store passes that store's policy. Besides the reserved paths every op is held to, a `link` op is checked for a live source, a rel in the edge vocabulary, a root-relative href, and a target that is a record in the head or the batch. It is not checked against the endpoint classes that `memhtml link` enforces in `@memhtml/store`, so a session `link` can join a task and a memory with a rel that `memhtml link` refuses for that pair.

A `move` or an `archive` leaves its old path, so a batch repoints the live edges to that path with `unlink` and `link` pairs. `withRepoints` adds those pairs, read from the view's inbound index, before the batch's first move or archive. `missingRepoints` finds the pairs a log already written lacks against the version it lands on, for the caller to append, and names under `overflow` each archive or move whose pairs would not fit under the cap. `afterDroppedVacates` works out what a log keeps when `session commit --drop-refused` drops an archive or a move: the repoint pairs it needed go with it. `VacateFollower` reports each op it took or rewrote.

`pruneSessions` removes session state that nothing reads again, each item only when it is older than `olderThanMs`. That is logs with zero ops, lock directories no live holder refreshes, and the `<id>.idx` index files and `SESSION_REFS_PREFIX` refs that older builds wrote. It never removes a log that holds ops, and lists one older than the cutoff under `unlanded` as an `UnlandedSession`, for an operator to commit. Outside a dry run it handles each id under that id's session lock, and either way an id whose lock is held is listed under `busy`. With `dryRun` it takes no lock, removes nothing, and reports what it would remove. `PruneReport` is the answer, with a `PruneCount` per kind of state.

`makePlumbing` returns the `Plumbing` the commit path runs: each method runs a `git -C` child with a few variables pinned and the `GIT_REPO_SELECTION_ENV` variables removed, so a `GIT_DIR` a hook exported cannot point a call at another repository. The four staging methods use the index file the plumbing was made with, so without one they cannot stage into the shared index. `PlumbingFactory` is how `commitSession` gets a plumbing for its temporary index, and a test seam. `RefEntry` is one row of `forEachRef`. `gitPathOf` asks git where a file under the git directory lives, because a linked worktree keeps `info/exclude` in its common directory.

`ensureExcluded` appends ignore patterns to the clone's `info/exclude`, each once, because a store's committed `.gitignore` may predate that state and rewriting it would dirty the tree. `ensureExcludedQuietly` is the best-effort form, which logs a failure and goes on. `startSession` passes `.memhtml/sessions/`, and the head server passes `HEAD_SOCKET`. `ExcludeResult` names the file and the patterns a call added. `GitFailure` is the shared class from `@memhtml/contracts`, re-exported so one `_tag` covers this package and the store. Its `command` is the git subcommand alone, never the arguments, because arguments carry memory paths and a failure goes back to an agent.
