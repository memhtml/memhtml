`@memhtml/curator` is the curator memhtml itself owns: a bounded tool loop in which a language model reads a corpus and proposes operations on it, with everything that loop needs except a store. It holds the two briefings code computes for the model, the two charters the model runs under, the six tools the model sees, the budget, the model factory behind `--model`, a scripted model that needs no credential, and the planner that cuts a corpus into clusters with no model call. Every model call the curator makes starts in this package, so the pins on `ai`, `@ai-sdk/amazon-bedrock`, `@ai-sdk/openai-compatible`, `@ai-sdk/provider` and `@aws-sdk/credential-providers` live in its `package.json`. It also depends on `@memhtml/contracts`, `@memhtml/domain`, `@memhtml/head`, `@memhtml/html`, `@memhtml/llm` and `@memhtml/session`, on `graphology` and three of its companion packages for the planner's graph, and on `zod` and `effect`. It opens no repository, no session and no sandbox: the search, read, exec, propose and status calls arrive as a `CuratorTools` value the caller builds.

Its one user outside tests is the CLI in `apps/cli`. `apps/cli/src/curate-run.ts` is the binder for `memhtml curate run`: it calls `curatorModel`, `briefingFromView`, `CURATOR_CHARTER` or `readCharterFile` with `renderCharter`, and `runCurator`, and implements `CuratorTools` over a loaded head, a session and the sandbox. `apps/cli/src/curate-collapse.ts` is the driver for `memhtml curate collapse`: it calls `planCollapse`, `parseRulings`, `renderCollapseBriefing`, `COLLAPSE_CHARTER`, `curatorModel` and `runCurator`, and sizes its sessions with `ARCHIVE_CHUNK` and `FOLD_FIRST_SESSION_MEMBERS`. `apps/cli/src/run.ts` judges a `--model` value with `modelSpecOf` before any repository opens, and `apps/cli/src/config.ts` reports `CURATOR_MODEL_VAR`. `memhtml curate merge`, the command that lands a curator branch, imports nothing from this package.

## A curate run

A curate run is one model-driven pass over one version of the corpus. `apps/cli/src/curate-run.ts::curateRun` resolves a branch, `curate/<UTC date>` unless `--ref` names another, and refuses a ref that is not under `refs/heads/curate/` (`apps/cli/src/curate-run.ts::curateRefProblem`) or that `HEAD` names. Without `--resume` it loads the version at `main`, or at `HEAD` in a repository with no `main` branch, and a run that is not a dry run starts a session on the curator ref. It computes the briefing and hands the model, the charter, the briefing and the tools to `runCurator`. Unless the run is a dry run, the loop ended on a model error, or the session holds no operation, it then commits the session's operations to the curator ref as one commit. The subject is `memhtml(curate):` and what `apps/cli/src/curate-run.ts::commitSummary` takes from the report, its first non-blank line when there is one, cut to the length `packages/session/src/commit.ts::commitSubject` allows. `curate run` and `curate collapse` each check the ref rule before a session opens. That rule is what keeps a run off `main` and off the working tree: on a fixture store a run created its `curate/` branch, wrote the session log and a snapshot under `.memhtml/`, and left `main`, `HEAD`, the files and `git status` as they were. Landing the branch is a separate command.

The package's own part of that is `runCurator`, which takes a `CuratorRunInput` and answers a `CuratorRun`: the model calls that completed, the token counts the provider reported, the report, `stoppedBy`, the operations the tools said they appended, the tool names in call order, and the failure text when there was one. It writes nothing itself. What reaches disk is whatever the caller's `CuratorTools` writes.

## The briefing

`briefingFromView` computes a `Briefing` from a `HeadView` with no model call and no I/O, and `renderBriefing` turns it into the one user message: a heading, the briefing as a fenced JSON block, and a closing instruction. `parseBriefing` reads the block back. The briefing counts active and archived records and the inbox's share, lists the active records with the lowest stated confidence, and names the work by path in eight lists, each sorted, capped, and carrying its uncapped total.

`duplicates` and `contradictions` come from frame keys: active records under one key that write the same value are a duplicate group, and a key whose records write two or more values is a contradiction. `task` and `verdict` records (`HEADLINE_CLAIM_TYPES`) join neither. `recent` is the active records, other than those two types and `resources/people/`, created after the newest other curator ref's commit date. The caller reads that date from git and passes it as `LastCurate`; with none, every such record is recent. Each recent record carries up to `BRIEFING_NEIGHBOR_CAP` neighbors from the caller's `NeighborsOf` search. The fields of `Briefing` below describe the other four lists: `unlabeled`, `supersededActive`, `danglingEdges` and `mootDetectedTasks`.

`inbox` is the placement list, built by `inboxWorkList`. A candidate is a directory under `areas/` or `resources/` that holds active records, other than the inbox, `areas/arcs/`, `resources/people/` and the store's writer buckets (`isBucketHome`). For each inbox record `isPlaceable` accepts, it scores every candidate by the record's entities and tags that name the directory and by the records there that carry the record's entities. The best candidate becomes the record's `CandidateHome` only when it is named by an entity or has `SHARED_MIN` carrier records, and strictly outscores the next. Failing that, an entity of a type in `NEW_HOME_TYPES` that `NEW_HOME_MIN` inbox records share names a new `resources/` directory. Any other record is listed with a null `home`. `InboxPolicy` carries the store's writer bucket patterns and its placement quota, and `inboxCapFor` sizes the list from the quota.

## The tools and the proposed operations

The model sees six tools, defined in `loop.ts`: `search`, `read`, `exec`, `propose`, `status` and `finish`. `search`, `read`, `exec` and `status` call the matching method of `CuratorTools`. `propose` calls it with the operations `toOverlayOps` resolved, when any remain. `finish` records the report and ends the run. Every result is serialized and cut at `TOOL_RESULT_CAP` characters by `truncateToolResult`, with a marker that says how much was dropped.

`ProposedOp` is the shape the model proposes, one of seven kinds: `ProposedPut`, `ProposedArchive`, `ProposedLink`, `ProposedUnlink`, `ProposedLabel`, `ProposedUnlabel` and `ProposedMove`. `toOverlayOps` turns a list of them into the overlay operations of `@memhtml/contracts`. An archive or a move names only paths, so the loop reads the source's bytes through `read`, and an archive with no `to` takes the year's first free slot from `archivePathFor`. A source `read` cannot find is left out and reported in `missing`, as `ProposedOverlayOps` shows, and the other operations of that call still go to `propose`. Whether an operation is accepted is the caller's decision: in the CLI binder each `propose` and each `exec` harvest is validated as a curator commit would be, and one violation appends nothing from that call and goes back to the model as the tool's result.

## The loop and how it stops

`runCurator` makes one `generateText` call with the charter as the system prompt, the briefing as the prompt, and four stop conditions checked after each model call. `StoppedBy` names the outcome, in this order of precedence. `finish` means the model called the `finish` tool, or the last model call carried text that is not blank while the signal was not aborted and the step limit was not reached, in which case that text is the report. `modelError` means the call threw while the run's signal was not aborted, and `error` carries the provider's status and URL or the failure's text. `wallClock` means the signal was aborted, by the `wallClockMs` timer or by the caller's own `signal`, which the loop does not tell apart. `maxOps` means the tools reported at least `maxOps` appended operations. `maxSteps` is every other stop: the step limit was reached, or the model answered with no tool call and no text before it. A stop other than `finish` gets a report the loop writes: the failure's text for `modelError`, and otherwise a sentence naming the limit of that stop reason.

`CuratorBudget` holds the four bounds, `DEFAULT_BUDGET` their defaults, and `budgetWith` fills a partial budget. `maxOps` defaults to the session's `BATCH_CAP`. `runCurator` reads the step limit, the operation limit and the wall clock from its `budget`; the output ceiling is set on the model, by `curatorModel`. Nothing carries a budget across runs. The operation limit is read between model calls, so the call that reaches it can pass it: with a limit of three and a tool that reported five, a probe run ended as `maxOps` with five appended. A tool method that throws does not end the run. The loop hands the model an `error` result naming the tool and the failure, and a probe whose `exec` threw still ended on `finish`. A run that stops without `finish` is not a failure of `runCurator`. The CLI binder treats every stop except `modelError` like a finished one. A fixture run held to two steps committed the operations its `exec` had appended, and its subject was the step limit's report.

## The model spec

`modelSpecOf` parses a spec string, after trimming, into a `CuratorModelSpec`: exactly `fake`, or `bedrock:` and a model id, or `proxy:` and a model name. Anything else, a different case or a prefix with nothing after the colon included, is a `ModelSpecRejected` with the reason. `parseModelSpec` is the same judgment as an effect that fails with `CuratorModelSpecInvalid`, and `MODEL_SPEC_PREFIXES` lists the three forms.

`curatorModel` builds the model and calls nothing. A `proxy:` spec goes through the LLM proxy: an OpenAI-compatible chat model at `/v1` under `MEMHTML_LLM_BASE_URL`, with the model named by `proxyModelId` from `@memhtml/llm`. With no such variable the spec fails with `CuratorModelSpecInvalid`. A `bedrock:` spec goes direct to Bedrock through `@ai-sdk/amazon-bedrock` in `AWS_REGION`, whether or not a proxy is configured, with the default credential provider chain unless `AWS_BEARER_TOKEN_BEDROCK` is set. `fake` builds `fakeCuratorModel` and reaches no network. Each of the three is wrapped by `withOutputCeiling`, so every call carries a `maxOutputTokens` setting. Against a loopback server a `proxy:` run posted to `/v1/chat/completions` with the prefixed model name and that setting in the body. The CLI picks the spec from `--model`, then from the variable `CURATOR_MODEL_VAR` names, then `proxy:` with `DEFAULT_CURATOR_MODEL_ID` when a proxy is configured. With none of the three it refuses at exit 2, as it does for a spec `modelSpecOf` rejects and for a `proxy:` spec with no proxy.

## The fake model

`fakeCuratorModel` is a scripted model whose next call `fakeNextCall` decides from the conversation so far. Under a curate-run briefing it calls `status`, then one `exec` with `fakeDedupScript`, which archives every record but the first of each `duplicates` group, links the kept record to each archive with `supersedes`, and cuts links whose target is no file. Then it makes one `propose` of the moves `fakePlacements` lists, the inbox records with an existing home up to the quota, when there are any, and calls `finish`. It leaves `contradictions` alone. Under a collapse briefing it makes the one proposal `fakeCollapseProposal` builds and finishes: the canonical and, unless the driver completes them, an archive for each member not ruled `keep`. On a fixture with one duplicate pair and one inbox record with a home, `curate run --model fake` made four model calls and landed one archive, one link and one move in one commit.

## The collapse planner

`planCollapse` cuts one `HeadView` into a `CollapsePlan` with no model call and no I/O. Rulings come first, when the caller passes them: `parseRulings` reads JSONL lines into `Ruling` values and throws on a line it cannot use, naming the line. A path ruled `archive` or `trace` joins an archive cluster, a path ruled `fold` with a theme joins that theme's fold, and a path ruled `keep` leaves every later cut. Without a ruling, records under `resources/people/` and `task` records are left out (`isShielded`). The rest is partitioned by source, the record's `memhtml-author` value (`sourceOf`), and memory type. Inside a partition, a frame key held by two or more records is a fold when `frameGroupAgrees` and a `keep` cluster when the records disagree.

The similarity clusters come last. `tfidfVectors` weighs each record's title, claim and body, `knnEdges` keeps each record's nearest neighbors at or above the similarity floor, shared entities add a second layer of edges, and `detectCommunities` cuts the graph with Louvain under a seeded generator (`seededRandom`). A community of two or more records that no frame-key group took is a fold, or a `keep` when it has more members than `maxFold`. Each `CollapseCluster` carries its `ClusterKind`, the `ClusterCut` that made it, its members, an anchor, a home directory from `homeFor`, and a rationale. `PlannerOptions` and `DEFAULT_PLANNER_OPTIONS` hold the settings and `PlanPolicy` the store's writer buckets and refused types. Two dry runs over one fixture commit on one day printed byte-identical plans. The plan is data, and the driver in `apps/cli/src/curate-collapse.ts` executes it: archive clusters with no model, and each fold as one curator session whose user message is `renderCollapseBriefing` under the collapse charter. A `CollapseBriefing` with `driverCompletes` set tells the model to write the canonical alone.

## Failure and resume

A model outage is a value, not a failure: `runCurator` answers `stoppedBy: "modelError"`. The CLI binder then exits 1 with `ERR_MODEL_UNAVAILABLE`, commits nothing, and leaves the session log in place. With a loopback server that answered every request with an error status, the run ended that way after the SDK's own retries, no ref was created, and a later `--resume` with the fake model landed a commit on the same ref. A refused operation never reaches the log, so it leaves nothing to undo. `runCurator` itself fails only with a `StorageFailure`, when it has to read the shipped charter and cannot; `readCharterFile` fails the same way for a file that cannot be read or has no text.

The commit is the binder's, through `@memhtml/session`, and it takes that package's checkout lock for the store directory. With the lock held by another writer for the whole wait, a fixture run exited 1 with `ERR_STORAGE` and `checkout.locked`, created no ref, and kept its three operations in the session log. A resume is a new `runCurator` call over the session's base plus its logged operations: the briefing is computed again, the model runs again, and the commit carries the logged operations and the new ones under the new report's first line. The resumed fixture run landed the three logged operations. One session id belongs to one ref in one store directory, so a second run on a ref without `--resume` is refused with `session.exists`, also after the first run committed.

## Beside `@memhtml/session` and `@memhtml/llm`

This package takes two things from `@memhtml/session`: the `Violation` type that `CuratorExecResult` and `CuratorProposeResult` carry, and `BATCH_CAP` for the default operation limit. It never starts, appends to, validates or commits a session; the binder does, and that package's page describes the log, the validator and the commit path. From `@memhtml/llm` it takes `modelByKey` for `DEFAULT_CURATOR_MODEL_ID`, and `proxyConfigFromEnv` and `proxyModelId` for the `proxy:` spec. The curator's requests are built by the `ai` SDK and its providers, not by that package's clients.
