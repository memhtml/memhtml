# memhtml-public · Debugging guide

Aligned to main at a219190 (0.15.1) on 2026-09-21.

When something is broken, this file says where to look first.

Two facts shape every entry below. First, the debugger is usually an agent, so the signal it reads is a JSON envelope on stdout plus an exit code. Every command writes exactly one envelope to stdout (`apps/cli/src/run.ts:1433-1435`) and sends its logs to stderr through `Logger.LogToStderr` (`apps/cli/src/run.ts:1817-1819`), and a failure envelope is `{apiVersion, error, code, suggestions}` (`apps/cli/src/envelope.ts:68-73`). An agent branches on `code` and not on the `error` prose, because the codes are append-only and the prose changes freely (`apps/cli/src/envelope.ts:75-79`). Two exceptions to the one-envelope rule are declared beside the response types: `help` on a terminal prints Markdown, and a successful `memhtml hook` prints a host's `hook.output` protocol rather than this envelope (`apps/cli/src/envelope.ts:50-52`).

Second, the state being debugged is not in this repository. This repo holds the software. The memories live in an external `memhtml root` directory that `$MEMHTML_ROOT` points at, defaulting to `~/memhtml` (`RUNBOOK.md:15`). The same binary serves many roots, and `--repo <path>` overrides the variable per call (`RUNBOOK.md:32`). "The tree is dirty" therefore refers to the root's git tree, and `.memhtml/index.db` inside the root is a rebuildable projection of that tree rather than a store of record (`RUNBOOK.md:358`).

Span export is opt-in and off unless an endpoint is set. `Effect.withSpan` wraps 29 call sites, and an OTLP trace exporter gated on `OTEL_EXPORTER_OTLP_ENDPOINT` ships in this repo (`packages/telemetry/src/index.ts:5-18`); with the variable unset, `layerTelemetry` is `Layer.empty` and the exporter module is never loaded, which is how both runtime assemblies provide it (`apps/cli/src/run.ts:1810-1816`, `apps/mcp/src/server.ts:55-61`). The exporter is effect's own `OtlpTracer` rather than the OpenTelemetry JS SDK, so no `@opentelemetry/*` dependency exists in any workspace package. With no endpoint configured, every diagnostic below reads stderr, a JSON envelope, or a file in the root.

## First-checks ladder

The checks are ordered cheapest first. Each one either explains the symptom or rules out a layer.

1. Run `memhtml manifest` and confirm it answers. It returns every command, argument, flag, response type, error code, and environment variable. It answers on a machine with no repo, no database, and no credentials, which makes it the liveness check when something else has failed. `apps/cli/src/commands.ts:1339-1343`, `apps/cli/src/run.ts:1449-1463`
2. Read the failure envelope's `code` instead of its `error` prose. The codes are append-only and a shipped code never changes meaning, while the prose changes freely as wording improves. `ERROR_CODES` holds twenty-one (`apps/cli/src/envelope.ts:80-115`), and an unrecognized upstream error class becomes `ERR_UNKNOWN` instead of crashing. `apps/cli/src/envelope.ts:67-87`, `apps/cli/src/errors.ts:41-42`
3. Read the envelope's `suggestions` array and run the first entry. Suggestions are part of the contract, and a suggestion has to be a call that MOVES the failure, since naming the command that raised the tag would loop, which is why `ERR_INDEX_STALE` suggests `memhtml index rebuild` and never `memhtml index update`, the command that raises it. An agent receiving that pair recovers in one step without a round trip to a human. When there are no suggestions the field is an empty array rather than a null. `apps/cli/src/errors.ts:120-158`
4. Confirm which root the command acted on. `memhtml status` reports `root`. The same binary serves many roots, with `$MEMHTML_ROOT` setting the default and `--repo <path>` overriding it per call. A memory that seems missing is often present in a different root. With `MEMHTML_REFUSE_ENV_ROOT` set, a call that opens a repo without `--repo` is refused with `ERR_REPO_REQUIRED` at exit 2 instead of defaulting to `~/memhtml`, which is the setting for CI and for an agent runtime that exports `MEMHTML_ROOT` to every subprocess. `apps/cli/src/operations.ts:2727`, `RUNBOOK.md:32`, `RUNBOOK.md:16`, `apps/cli/src/envelope.ts:88-90`
5. Read `indexFresh` and `embedderUp` from `memhtml status`. `indexFresh` compares the recorded watermark to HEAD, which is the accurate comparison because the index is a projection of a commit. `embedderUp` is read off the stored watermark instead of by probing Bedrock, so it does not fail for a reason unrelated to the corpus. `apps/cli/src/operations.ts:2663-2669`, `apps/cli/src/operations.ts:2705`, `apps/cli/src/operations.ts:2744`
6. Run `memhtml doctor` for the eleven corpus checks, the eleventh being vector coverage (`apps/cli/src/doctor.ts:70-76`; the file's own header line still says ten at `apps/cli/src/doctor.ts:36`, which `RUNBOOK.md:267` does not). The floor is `MEMHTML_VECTOR_COVERAGE_FLOOR` (`apps/cli/src/config.ts:213`, `apps/cli/src/doctor.ts:75-76`), and a value of 0, a negative, or a value above 1 aborts layer construction naming the variable instead of falling back to the default (`apps/cli/src/api-layer.ts:297-312`). `healthy` is computed from the findings rather than from a repair. Three findings are excluded from it: `overdueTasks` and `staleBlockers`, because those describe the state of the work rather than defects in the corpus, and `untypedEntities`, because `unknown` is a supported storage type and a bare entity name is therefore a reachability cost rather than a defect. `apps/cli/src/doctor.ts:705-724`
7. Read stderr for the layer the envelope withheld. Each typed error class drops the driver message, the SQL, the git argv (`packages/store/src/git.ts:30-33`), and every memory body (`apps/cli/src/errors.ts:84-88`) at its adapter edge, so a tool response cannot carry corpus content. The detail goes to `Effect.logError` instead. `packages/contracts/src/errors.ts:3-8`, `packages/index/src/database.ts:157-162`
8. If the symptom is retrieval quality with no error at all, run `memhtml eval discriminate`. Every probe must outrank its own wrong-fact twins against the `MRR_FLOOR` default of `0.85`, and a failing run is reproducible from its `seed`. `packages/eval/src/discriminate.ts:99-104`, `packages/eval/src/run.ts:92`, `RUNBOOK.md:255-258`
9. If the index looks structurally wrong, rebuild it. `memhtml index rebuild --embed` deletes every memory table, reprojects the tree through the live FTS triggers, and keeps every stored vector whose content-addressed chunk id comes back; only a model change empties the vector plane (`packages/index/src/indexer.ts:375-416`). A store-wide vector gap needs no rebuild at all: `memhtml index embed` fills it in place. It deletes nothing outside `.memhtml/`, and it touches neither the trace tables nor the attached state plane. A deleted database mostly handles itself, because `update` with no recorded watermark falls through to a rebuild. `packages/index/src/indexer.ts:538-540`, `RUNBOOK.md:137-139`
10. As a last resort, reclone the root and reproject. Run the steps in this order. `memhtml init` comes first because the merge driver is per-clone. `memhtml state import` comes before the rebuild so the salience arm has signal on the first query. `memhtml index rebuild --embed` comes last because it is the only step that costs Bedrock calls, and it is the step to re-run if the sequence is interrupted. `RUNBOOK.md:342-356`

## Load-bearing guards and the failure each one prevents

This codebase carries no `INCIDENT:` or `POSTMORTEM:` comment tags and holds exactly one file under `docs/bugs/`. Each guard's rationale is recorded inline at the code that enforces it. Every entry below names the guard, the signal you would see if it came off, and where it lives, so an unexplained symptom in this list is a hint about which guard to check first. **Removing any one of these is a regression, not a simplification.**

- **A tool failure is a `ToolFailure`, never an `AiError`:** `McpServer` catches an `AiError` FIRST and rewrites it to a generic internal-error sentence unless its reason is a parameter-validation error, so `handled` builds a `ToolFailure` and every tool declares `failure:` in its schema, which puts the failure on the branch that passes `.message` through verbatim. Signal if either half comes off: every typed failure reaches its agent with the content removed. The two halves work only together, and dropping the declaration in `apps/mcp/src/tools.ts` re-masks everything the translation builds. The three-branch observation these guards rest on is pinned in the source to effect 4.0.0-rc.109 and was not re-verified at the pinned rc.117 (`apps/mcp/src/failure.ts:10`, `apps/mcp/src/handlers.ts:63`, `apps/mcp/src/tools.ts:49`, `pnpm-workspace.yaml:93`). `apps/mcp/src/handlers.ts:58-70`
- **The consolidation watermark covers the READ set, not the asked-about set:** the two differ for either of two reasons, and the phase holds only the intersection so it cannot separate them. A transcript may not reach the agent: rotated away since `memhtml trace index` ran, moved outside `MEMHTML_TRACE_ROOT`, or behind a symlink the read-only mount will not follow. Or it reaches the agent and the answer's `readSessionIds` receipt does not name it. So `batch` minus `consolidated` is reported as `unconsolidated` rather than as `unreachable`, because a key naming one cause while carrying two is the mislabeled-number defect this repo has paid for. `ConsolidationOutcome` cannot be constructed without `analyzedSessionIds`, so this is a structural guard rather than a check. Signal if it comes off: a session recorded as consolidated that nothing read, and because `trace_consolidations` is an anti-join, that transcript is never selected again. `packages/sleep/src/phases/trace-consolidation.ts:49-53`, `packages/sleep/src/phases/trace-consolidation.ts:1055-1068`, `packages/sleep/src/phases/trace-consolidation.ts:1282-1299`, `apps/consolidator/src/contract.ts:409-410`
- **`SUGGESTIONS` is a record, not a switch, because a record's keys and arms are both walkable:** the suite enumerates every tag, runs every suggestion string through the real `parseArgv`, and fails on a name the command table does not hold, so a command rename in `apps/cli/src/commands.ts` cannot leave a suggestion behind. Signal if the walk comes off: an agent follows a suggestion into `ERR_UNKNOWN_COMMAND`. `apps/cli/src/errors.ts:138-142`
- **The `<mark>` gate checks non-emptiness as well as count and placement:** `<p><mark></mark> the prose</p>` satisfies both of the other two rules, and the emptiness predicate is the `files.gist` rule verbatim (`canonicalText` with `excludeCode`, then trimmed) so the gate cannot disagree with the column. Both write doors deriving a claim from prose are the second layer. Signal if it comes off: a committed, indexed file with an empty `files.gist`, absent from every disclosure tier and from the recall pack's quoted body, a memory that does not appear at all rather than appearing wrong. `packages/html/src/constraints.ts:154`, `packages/html/src/constraints.ts:166-209`
- **`article_html` reaches disk verbatim, and `@memhtml/store` re-parses it before anything is staged:** the prose path entity-escapes its argument, so the markup path is the only way a `<time datetime>`, and therefore `files.event_at`, is reachable from an agent, and the render gate is what keeps that passthrough from admitting a malformed file. Signal if the passthrough comes off: `event_at` stays NULL and the recency arm's `coalesce(event_at, updated_at)` ranks every agent-written memory by write time, so episodic memories sort by when they were written down instead of when the fact happened. Filed and resolved 2026-08-03: `docs/bugs/2026-08-03-event-at-unreachable-through-write-paths.md:1-18`
- **The consolidation turn's bounds are enforced in the process that makes the model calls:** `generateText` runs the tool loop in this process, and the step count, the turn's output-token total, and the wall clock through `abortSignal` are all stated in that one call and nowhere else. Signal if the loop moves back out of process: the previous runtime ran the same loop in a spawned server behind an HTTP client, where every one of its bounds turned into a cooperative signal a wedged server never observed. `apps/consolidator/src/turn.ts:16-26`
- **Per-batch index costs are scoped to the batch, never to the store:** one full-tree walk plus a batched blob read rather than a per-file walk, and a pending-embedding scan scoped to the batch's own chunk ids. Signal if either scoping comes off: an incremental `index update` whose duration grows with corpus size instead of batch size. Probed 2026-08-05, a tree walk costs 49ms over 10k files, so a per-file walk is 2N walks, 25 seconds of a 48-second update at N=256 (`packages/index/src/indexer.ts:866`). The unscoped pending scan measures linear at 11ms over 1k chunks and 60ms over 10k, probed 2026-08-06 (`packages/index/src/indexer.ts:462`). The whole-store scan is still REQUIRED for `memhtml index rebuild --embed`, which is the model migration and must see every chunk (`packages/index/src/indexer.ts:538-540`).
- **Two doctor predicates are mutation-verified rather than assumed** (2026-08-02). `archived = 0` and `task_status <> 'done'` on the `overdueTasks` query: dropping either makes the finding grow forever and never reach zero, because a finished task's deadline stays in the past. The `missing` arm of the stale-blocker check is unreachable today, because deleting a blocker's file makes `indexer.update` clear `edges WHERE src_path = ?` in the same batch; it stays because `edges` carries no foreign key by design, so a future writer of edge rows would not inherit the indexer's discipline. `apps/cli/src/doctor.ts:321-333`, `apps/cli/src/doctor.ts:353-358`
- **Both JSON-Schema derivation sites pass `{ onExcessProperty: "error" }`, and the strict decode depends on it:** `toInputSchema` in `@memhtml/llm` and the consolidator's own `toJsonSchema` both hand the option to `Schema.toJsonSchemaDocument`, and `decodeToolInput` decodes with the same option, because the default, `"ignore"`, strips an undeclared key and succeeds. Signal if either derivation drops the option under the pinned effect rc.117: a model answer carrying excess properties passes the strict decode instead of raising `LlmContractViolation`, a silent wrong answer where a typed failure was designed. `packages/llm/src/structured.ts:45`, `packages/llm/src/structured.ts:116-119`, `packages/llm/src/structured.ts:142`, `apps/consolidator/src/contract.ts:738`, `pnpm-workspace.yaml:93`
- **The consolidator keeps its own copy of the proxy parsers, and the two copies must agree:** the consolidator's agent file cannot import a workspace package, so `apps/consolidator/src/llm-proxy.ts` re-declares the proxy variable names and `proxyModelPrefix`, and one environment variable is resolved by two readers. That is why `PROXY_MODEL_PREFIX_NONE` is the word `none` rather than `""`: `effect/Config` reads an empty value as absent, so `""` would have meant the default on the sleep lanes and no prefix in the consolidator. Signal if the copies drift: the sleep lanes and the consolidator ask the same proxy for different model ids under one configuration. `apps/consolidator/src/llm-proxy.ts:31`, `apps/consolidator/src/llm-proxy.ts:36-37`, `apps/consolidator/src/llm-proxy.ts:48-52`, `packages/llm/src/proxy-config.ts:57-65`, `packages/llm/README.md:9`
