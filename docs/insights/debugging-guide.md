# memhtml-public · Debugging guide

Describes the source at 0.16.0 (2026-10-18). Citations are `path:line` into that tree.

When something is broken, this file says where to look first.

Three facts shape every entry below. First, the debugger is usually an agent, so the signal it reads is a JSON envelope on stdout plus an exit code. Every command writes one envelope through `emit` (`apps/cli/src/run.ts:1693-1696`), and logs go to stderr through `Logger.LogToStderr` (`apps/cli/src/run.ts:2440-2442`). A failure envelope is `{apiVersion, error, code, suggestions}` (`apps/cli/src/envelope.ts:98-103`). An agent branches on `code` and never on the `error` prose, because the codes are append-only and the prose changes freely (`apps/cli/src/envelope.ts:105-109`). Two exceptions to the one-envelope rule are declared beside the response types. `help` on a terminal prints Markdown, and a successful `memhtml hook` prints a host's hook protocol instead of the envelope (`apps/cli/src/envelope.ts:51-54`).

Second, the state being debugged isn't in this repository. This repo holds the software. The memories live in an external memhtml root that `$MEMHTML_ROOT` names, `~/memhtml` by default (`RUNBOOK.md:15`), and `--repo <path>` overrides it per call (`apps/cli/src/commands.ts:76-79`). "The tree is dirty" means the root's git tree. `.memhtml/index.db` inside the root is a rebuildable projection of that tree, and the tree is the system of record (`RUNBOOK.md:358`).

Third, a v2 call can be answered by two processes. `head status`, `head search`, `session put`, `session exec`, `session commit`, and `session rebase` ask the head server on `.memhtml/head.sock` first and load the corpus locally when no server answers (`apps/cli/src/v2.ts:130-137`). MCP `memory_search` and `memory_recall` do the same and fall back to the SQLite index (`apps/cli/src/head-retrieval.ts:19-32`). So "which path answered" is often the first question, and the last section of the index says how to read it.

Span export is opt-in. `Effect.withSpan` wraps 32 call sites across 17 source files, and an OTLP trace exporter gated on `OTEL_EXPORTER_OTLP_ENDPOINT` ships in this repo (`packages/telemetry/src/index.ts:5-18`). With the variable unset, `layerTelemetry` is `Layer.empty` and the exporter module is never loaded, which is how both runtime assemblies provide it (`apps/cli/src/run.ts:2432-2439`, `apps/mcp/src/server.ts:55-61`). The exporter is effect's own `OtlpTracer`, so no `@opentelemetry/*` dependency exists in any workspace package. With no endpoint configured, every diagnostic below reads stderr, a JSON envelope, or a file in the root.

## First-checks ladder

The checks are ordered cheapest first. Each one either explains the symptom or rules out a layer.

1. Run `memhtml manifest` and confirm it answers. It returns every command, argument, flag, response type, error code, and environment variable. It answers on a machine with no repo, no database, and no credentials, which makes it the liveness check when something else has failed. `apps/cli/src/commands.ts:1779-1798`, `apps/cli/src/run.ts:1705`
2. Read the failure envelope's `code` instead of its `error` prose. The codes are append-only and a shipped code never changes meaning, while the prose changes freely as wording improves. `ERROR_CODES` holds 25 (`apps/cli/src/envelope.ts:110-161`), and an unrecognized upstream error class becomes `ERR_UNKNOWN` instead of crashing. `apps/cli/src/errors.ts:42-43`, `apps/cli/src/errors.ts:99-100`
3. Read the envelope's `suggestions` array and run the first entry. Suggestions are part of the contract, and a suggestion has to be a call that moves the failure, since naming the command that raised the tag would loop. That's why `ERR_INDEX_STALE` suggests `memhtml index rebuild` and never `memhtml index update`, the command that raises it. When there are no suggestions the field is an empty array. Every `StorageFailure`, the v2 lock and log operations included, carries none. `apps/cli/src/errors.ts:169-188`, `apps/cli/src/errors.ts:272-275`
4. Confirm which root the command acted on. `memhtml status` reports `root`. The same binary serves many roots, with `$MEMHTML_ROOT` setting the default and `--repo <path>` overriding it per call. A memory that seems missing is often present in a different root. With `MEMHTML_REFUSE_ENV_ROOT` set, a call that opens a repo without `--repo` is refused with `ERR_REPO_REQUIRED` at exit 2, which is the setting for CI and for an agent runtime that exports `MEMHTML_ROOT` to every subprocess. `apps/cli/src/operations.ts:2534`, `RUNBOOK.md:16`, `apps/cli/src/envelope.ts:118-120`
5. Check the process environment for `MEMHTML_SESSION`. Set, it's the default `--id` of every `session` command, it starts that session on first use, and it closes the v1 record doors under the default `v1Doors`. A test suite or a shell inside an agent run inherits it without asking. `apps/cli/src/config.ts:83-105`, `apps/cli/src/config.ts:132`
6. For a v2 command, read where the answer came from: `data.head.source`, and on a commit or rebase `data.via` and `data.server.reason`. Then run `memhtml head status` to see whether a server runs and which sha it holds. A server that follows another ref answers `other-ref`, and the CLI commits locally. `apps/cli/src/v2.ts:151-176`, `apps/cli/src/v2.ts:1353-1375`
7. For a session, run `memhtml session status --id <id>`. It reads the log and the ref without loading the corpus, and it says whether the ref moved past the base (`behind`), how many ops wait, and whether a commit is `pending`. `apps/cli/src/v2.ts:1272-1297`
8. Run `memhtml config` when a write is refused and the reason names the bar or a door. It reports every policy key with its value and its source, and whether the policy file is committed. `apps/cli/src/config-report.ts:77-84`
9. Read `indexFresh` and `embedderUp` from `memhtml status`. `indexFresh` compares the recorded watermark to `HEAD`, which is the accurate comparison because the index is a projection of a commit. `embedderUp` is read off the stored watermark instead of by probing Bedrock, so it doesn't fail for a reason unrelated to the corpus. `apps/cli/src/operations.ts:2473-2487`, `apps/cli/src/operations.ts:2512`, `apps/cli/src/operations.ts:2551`
10. Run `memhtml doctor` for the ten corpus checks, the tenth being vector coverage (`apps/cli/src/doctor.ts:34-74`). The floor is `MEMHTML_VECTOR_COVERAGE_FLOOR`, and an unusable value aborts layer construction naming the variable (`apps/cli/src/api-layer.ts:296-303`). `healthy` is computed from the findings and never from a repair. Three findings are excluded from it. `overdueTasks` and `staleBlockers` describe the state of the work and aren't defects in the corpus, and `untypedEntities` is excluded because `unknown` is a supported storage type, so a bare entity name is a reachability cost. `apps/cli/src/doctor.ts:631-668`
11. Read stderr for the layer the envelope withheld. Each typed error class drops the driver message, the SQL, the git argv, and every memory body at its adapter edge, so a tool response can't carry corpus content. The detail goes to `Effect.logError` instead. `packages/contracts/src/errors.ts:3-8`, `packages/contracts/src/errors.ts:13-23`, `apps/cli/src/errors.ts:104-112`
12. If the symptom is retrieval quality with no error at all, run `memhtml eval discriminate` for the index and `memhtml head search` for the head. Every discrimination probe must outrank its own wrong-fact twins against the `MRR_FLOOR` default of `0.85`, and a failing run is reproducible from its `seed`. The head ranks with BM25 and the vector arm only, with no salience arm and no MMR, so the two doors can order the same records differently. `packages/eval/src/discriminate.ts:99-104`, `packages/eval/src/run.ts:92`, `apps/cli/src/head-retrieval.ts:29-32`
13. If the index looks structurally wrong, rebuild it. `memhtml index rebuild --embed` deletes every memory table, reprojects the tree through the live FTS triggers, and keeps every stored vector whose content-addressed chunk id comes back. Only a model change empties the vector plane. A store-wide vector gap needs no rebuild, because `memhtml index embed` fills it in place. The rebuild deletes nothing outside `.memhtml/` and touches neither the trace tables nor the attached state plane. `packages/index/src/indexer.ts:536-541`, `packages/index/src/indexer.ts:704-712`
14. As a last resort, reclone the root and reproject. Push or commit every session first, because `.memhtml/sessions/` is gitignored and a reclone loses every log that still holds ops. `memhtml init` comes first because the merge driver is per clone. `memhtml state import` comes before the rebuild so the salience arm has signal on the first query. `memhtml index rebuild --embed` comes after them because it's the step that costs Bedrock calls, and it's the step to re-run if the sequence is interrupted. `memhtml head embed` refills the head's vector cache, which is gitignored too. `RUNBOOK.md:338-356`, `packages/store/src/layout.ts:75-89`

## Guards and the failure each one prevents

This codebase carries no `INCIDENT:` or `POSTMORTEM:` comment tags. Each guard's rationale is recorded inline at the code that enforces it. Every entry below names the guard, the signal you'd see if it came off, and where it lives, so an unexplained symptom in this list is a hint about which guard to check first. Removing any one of these is a regression.

- **A tool failure is a `ToolFailure`, never an `AiError`.** `McpServer` catches an `AiError` first and rewrites it to a generic internal-error sentence unless its reason is a parameter-validation error. So `handled` builds a `ToolFailure` and every tool declares `failure:` in its schema, which puts the failure on the branch that passes `.message` through verbatim. If either half comes off, every typed failure reaches its agent with the content removed. The two halves work only together, and dropping the declaration in `apps/mcp/src/tools.ts` re-masks everything the translation builds. The three-branch observation these guards rest on is pinned in the source to effect 4.0.0-rc.109 and wasn't re-verified at the pinned 4.0.5 (`apps/mcp/src/failure.ts:10`, `apps/mcp/src/handlers.ts:67`, `apps/mcp/src/tools.ts:49`, `pnpm-workspace.yaml:61`). `apps/mcp/src/handlers.ts:55-77`
- **`SUGGESTIONS` is a record, because a record's keys and arms are both walkable.** The suite enumerates every tag, runs every suggestion string through the real `parseArgv`, and fails on a name the command table doesn't hold, so a command rename in `apps/cli/src/commands.ts` can't leave a suggestion behind. If the walk comes off, an agent follows a suggestion into `ERR_UNKNOWN_COMMAND`. `apps/cli/src/errors.ts:178-182`, `apps/cli/tests/cli.test.ts:740-760`
- **The `<mark>` gate checks non-emptiness as well as count and placement.** `<p><mark></mark> the prose</p>` satisfies both of the other two rules, and the emptiness predicate is the `files.gist` rule verbatim (`canonicalText` with `excludeCode`, then trimmed), so the gate can't disagree with the column. If it comes off, a committed, indexed file has an empty `files.gist` and is absent from every disclosure tier and from the recall pack's quoted body. The memory doesn't appear at all, which is harder to notice than one that appears wrong. `packages/html/src/constraints.ts:156`, `packages/html/src/constraints.ts:174-211`
- **`article_html` reaches disk verbatim, and `@memhtml/store` re-parses it before anything is staged.** The prose path entity-escapes its argument, so the markup path is the only way a `<time datetime>`, and therefore `files.event_at`, is reachable from an agent. The render gate keeps that passthrough from admitting a malformed file. If the passthrough comes off, `event_at` stays NULL and the recency arm's `coalesce(event_at, updated_at)` ranks every agent-written memory by write time, so episodic memories sort by when they were written down instead of when the fact happened. Filed and resolved 2026-08-03 in `docs/bugs/2026-08-03-event-at-unreachable-through-write-paths.md:1-18`.
- **Per-batch index costs are scoped to the batch, never to the store.** One full-tree walk plus a batched blob read replaces a per-file walk, and the pending-embedding scan is scoped to the batch's own chunk ids. If either scoping comes off, an incremental `index update` takes time that grows with corpus size instead of batch size. Probed 2026-08-05, a tree walk costs 49 ms over 10k files, so a per-file walk is 2N walks, 25 seconds of a 48-second update at N=256 (`packages/index/src/indexer.ts:866`). The unscoped pending scan measures linear at 11 ms over 1k chunks and 60 ms over 10k, probed 2026-08-06 (`packages/index/src/indexer.ts:462`). The whole-store scan is still required for `memhtml index rebuild --embed`, which is the model migration and must see every chunk (`packages/index/src/indexer.ts:536-541`).
- **Two doctor predicates are mutation-verified** (2026-08-02). `archived = 0` and `task_status <> 'done'` on the `overdueTasks` query matter, because dropping either makes the finding grow forever and never reach zero, since a finished task's deadline stays in the past. The `missing` arm of the stale-blocker check is unreachable today, because deleting a blocker's file makes `indexer.update` clear `edges WHERE src_path = ?` in the same batch. It stays because `edges` carries no foreign key by design, so a future writer of edge rows wouldn't inherit the indexer's discipline. `apps/cli/src/doctor.ts:289-291`, `apps/cli/src/doctor.ts:321-326`
- **The structured-output lane passes `{ onExcessProperty: "error" }` at both of its sites, and the strict decode depends on it.** `toInputSchema` in `@memhtml/llm` hands the option to `Schema.toJsonSchemaDocument`, and `decodeToolInput` decodes with the same option, because the default, `"ignore"`, strips an undeclared key and succeeds. If the option comes off under the pinned effect 4.0.5, a model answer carrying excess properties passes the strict decode instead of raising `LlmContractViolation`, a silent wrong answer where a typed failure was designed. `packages/llm/src/structured.ts:45`, `packages/llm/src/structured.ts:116-119`, `packages/llm/src/structured.ts:142`, `pnpm-workspace.yaml:61`
- **Every write of a session log re-reads the log under the session's lock and compares its ops.** A `session exec` reads the log, runs a script for seconds, and then appends, so the lock alone would still lose an update when two execs read the same log. `requireLogUnmoved` refuses with `session.moved` instead. If it comes off, the second writer drops the first one's ops with no error. `packages/session/src/session.ts:27-35`, `packages/session/src/session.ts:311-319`
- **A commit writes `pending` to the log before it touches anything shared.** A process killed at any later instant leaves a record, and the next commit settles it under the checkout lock. A commit that reached the ref answers `committed` with `recovered: true`, and one that didn't is undone with a two-tree `read-tree -m -u`. If it comes off, a commit killed after its swap leaves ops that the next call refuses as duplicates of themselves. `packages/session/src/session.ts:46-52`, `packages/session/src/commit.ts:405-408`, `packages/session/src/commit.ts:465-491`
- **The checkout lock covers both kinds of writer of the shared index.** The v1 store holds it from its first stage to its commit, and a session commit holds it around the checkout update, the compare-and-swap, and the rollback. Interleaved without it, a v1 commit sweeps the session's staged file into its own commit, the session's swap loses, and the next v1 commit removes the file from the branch. `packages/contracts/src/checkout-lock.ts:5-29`, `packages/session/src/commit.ts:267-282`
- **Every `OverlayOp` kind has a decoder branch, checked at compile time.** `everyKindDecodes` is a type that fails to build when the contract gains a kind the log's schema lacks. If it comes off, `appendOps` writes a log that `resumeSession` refuses with `session.decode`, and every later call on the session fails. `packages/session/src/session.ts:112-122`
- **The head client calls a request lost only after the connection completed.** Any failure before the connect completes means no byte reached a server, so the CLI falls back to the local path. A failure after it completes may follow a request the server read, so a commit, rebase, or exec fails with `ERR_STORAGE` and isn't repeated. If the phase test comes off in one direction, a server that's down fails every call. If it comes off in the other, a run-end commit lands twice. `apps/cli/src/head-client.ts:21-25`, `apps/cli/src/head-client.ts:189-217`
- **The store policy decodes strictly and fails closed.** An unknown key (`requireAnchors` for `requireAnchor`) is a refusal, never an unset key, because a typo in a policy file must not loosen the policy it states. If it comes off, a misspelled `requireAnchor` turns the anchor rule off with no signal. `packages/contracts/src/store-config.ts:14-17`, `packages/contracts/src/store-config.ts:187`
