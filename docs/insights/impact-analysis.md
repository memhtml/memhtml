# memhtml-public · Impact analysis

Describes the source at 0.16.0 (2026-10-18). Citations are `path:line` into that tree.

If you change surface X, this file lists what else you have to think about.

**A surface is high-impact here when changing it forces edits in more than one workspace package.** The ranking metric is the number of distinct workspace packages that reach the surface in the import graph, with the raw count of importing files as the tie-break. Raw inbound-file count isn't the metric, because a contract surface can have the widest blast radius without having the most importers. `packages/integrations/src/types.ts` has 28 importing files, and 24 of them sit inside `packages/integrations`. `packages/contracts/src/store-config.ts` has 17 and reaches six packages. Fan-out inside one package is refactoring work in one directory. Fan-out across packages is a change that has to land in agreement across a build graph.

Some destinations on this list have a blast radius that reaches past the build graph, and each carries a note saying so.

- **Reaches existing roots.** This repository stores no memory. It's the software that manages a separate directory called the memhtml root, located by `MEMHTML_ROOT` (`apps/cli/src/config.ts:107-126`, `apps/cli/src/config.ts:278-282`). Every root that already exists holds files written by whatever version of this software created them. The memory file format (`packages/html`), the root's on-disk layout (`packages/store/src/layout.ts`), the store policy file committed at the root (`packages/contracts/src/store-config.ts`), and the caches and session logs under `.memhtml/` (`packages/snapshot`, `packages/session`) are all data this repository doesn't contain and can't migrate in a commit.
- **Reaches installed hosts.** `packages/integrations` writes into a host's configuration directory, outside both this repository and the root, at `$HOME` for user scope and the git top level for project scope (`packages/integrations/src/hosts.ts:155-160`). At user scope that means `~/.claude.json`, `~/.claude/settings.json`, `~/.claude/CLAUDE.md`, and the installed skill (`packages/integrations/src/hosts.ts:168-175`), and the matching files under `~/.codex`, `~/.cursor`, and `~/.config/opencode` (`packages/integrations/src/hosts.ts:196-260`). `apps/cli/src/integrations.ts:88` resolves the user-scope root to `homedir()`.
- **Reaches running processes.** Two contracts hold between processes, which may come from different installs of this software. The head server protocol is spoken between a long-running `memhtml head serve` and every CLI and MCP process that asks it first (`apps/cli/src/head-protocol.ts:7-16`). The checkout lock is shared by every writer of a store's git index in any process (`packages/contracts/src/checkout-lock.ts:5-28`). A process built before 0.16 takes no checkout lock at all.

The primary consumer of every surface below is a coding agent rather than a person at a terminal. A change to the JSON envelope is high-impact because agents parse it and branch on it. A change to a closed vocabulary is high-impact because that vocabulary is published in the machine-readable manifest an agent reads before its first call.

Ranking data was measured on 2026-10-18 by walking every `.ts`, `.mts`, `.mjs`, and `.js` file under `packages`, `apps`, `tests-integration`, and `scripts`, 471 files in all, skipping `node_modules`, `dist`, and build output. Relative specifiers were resolved by path. Each `@memhtml/*` import was resolved symbol by symbol to the file that defines the imported name, through the package's `src/index.ts` re-exports and through any module that imports a name and exports it again. The barrel files' own re-export lines don't count as importers. So a barrel import of one `@memhtml/domain` symbol credits one domain file. Packages are counted as each `apps/*` and `packages/*` directory, plus `tests-integration` and `scripts`.

`Touch on change` reads as follows. `yes` means the consumer must be edited when the surface changes shape. `likely` means the consumer needs review even without a signature change, usually because it restates the surface's content somewhere the type system can't check. `no` means only a behavioral change reaches it.

### Blast-radius notes

- Each error class carries only summary detail. `StorageFailure` carries an operation name, and the driver's own message goes to `Effect.logError` at the adapter edge (`packages/contracts/src/errors.ts:3-11`). `GitFailure` carries the subcommand name and never the argv (`packages/contracts/src/errors.ts:13-28`). The contract is that the payload is safe to return to an agent. Adding a field that carries SQL text, git argv, or a memory body would let corpus content reach a tool response. The v2 lost-answer failures put a sentence into `operation`, including up to 200 characters of the transport's own detail (`apps/cli/src/v2.ts:908-913`, `apps/cli/src/v2.ts:1070-1075`), so that field holds text from another process as well as a name.
- `GitFailure` is declared here because two packages spawn git, the store and the session (`packages/contracts/src/errors.ts:19-23`). The doc block above `codeFor` puts it in `@memhtml/store` and calls it the one class outside the contracts package, and both halves of that are out of date (`apps/cli/src/errors.ts:35-37`). `codeFor` also maps nine classes declared outside this file. `EmbedModelMismatch`, `IndexStale`, and `RebuildNoEmbedRefused` come from `packages/index/src/indexer.ts:159-199`, `DiscriminationFailed` from `packages/eval/src/run.ts:167`, `HeadGateFailed` from `packages/head/src/gate.ts:264`, `IntegrationModified` from `packages/integrations/src/errors.ts:8`, `CuratorModelSpecInvalid` from `packages/curator/src/errors.ts:7`, and `HeadServerRunning` and `HeadSocketPathTooLong` from `apps/cli/src/head-protocol.ts:837-860`. A new class without a `codeFor` arm yields `ERR_UNKNOWN`, because the switch has a `default` (`apps/cli/src/errors.ts:99-100`), and nothing in the type system catches the omission.
- `V1DoorClosed` maps to two codes by payload. A set `session` is `ERR_SESSION_BOUND` and an absent one is `ERR_V1_DOOR_CLOSED` (`apps/cli/src/errors.ts:96-98`). The MCP door rewrites its reason as well as its suggestions, because the CLI wording names commands an MCP agent can't run (`apps/mcp/src/failure.ts:152-166`). A change to the class's fields reaches both tables and both reason writers.
- `packages/domain` names `InvalidMemory` as a type only, and `packages/domain/tests/layering.test.ts` reads the emitted `dist/` to check that domain's runtime imports stay limited to `effect` (`packages/domain/src/index.ts:1-6`, `packages/domain/tests/layering.test.ts:7-14`). Turning that type import into a value import fails that test, so it costs more than adding a dependency.

### Blast-radius notes

- `archivePathFor` and `originalPathFor` are a matched pair. Archiving mirrors the whole original path beneath `archive/<YYYY>/`, which makes the mapping injective and invertible, so `git log --follow` reads through an eviction and `diff -M` reports it as `R100` (`packages/contracts/src/paths.ts:208-218`). `originalPathFor` strips exactly one prefix, so it stays a left inverse even for a memory archived twice (`packages/contracts/src/paths.ts:220-229`). Both doors depend on it now. The v1 store computes archive paths with it, and the session's write bar refuses an archive op whose destination doesn't invert to its source. Changing either side without the other breaks archive round-tripping on every root that already holds archived files, and it makes the session door refuse archives the v1 door still writes.
- `placementFor` is total. It always returns a directory rooted in a PARA bucket, so the v1 write path never fails on placement (`packages/contracts/src/paths.ts:132-148`). An unusable explicit `path` is ignored instead of propagated, and a caller that wants it refused gates on `memoryPathViolation` first, which is what the store's `strictPath` and the session's write bar both do.
- The `tasks` segment name is part of the contract. Keeping tasks in one named segment is what makes `ls projects/<slug>/tasks` the list operation (`packages/contracts/src/paths.ts:24-33`), and the curator's inbox placement leaves `areas/inbox/tasks/` alone by that name (`packages/curator/src/inbox.ts:142`, `packages/curator/src/inbox.ts:191`). Renaming it orphans every task file in every existing root, because nothing migrates them.

### Blast-radius notes

- `MEMORY_TYPES`, `PARA_BUCKETS`, and `TASK_STATUSES` are restated in SQL, and so are the `Importance` and `Confidence` ranges (`packages/index/migrations/0001_files.sql:36-37`, `packages/index/migrations/0008_tasks.sql:48-49`). `MEMORY_TYPES` and `PARA_BUCKETS` are restated twice, once in each migration that creates `files`. No compiler checks that agreement. The v2 path makes the gap wider. A memory type added here without a migration passes the parser, the head, and a session commit, and the index is the only layer that refuses it, with a CHECK failure the first time it projects the file.
- A type removed here makes every `memhtml.config.json` that names it in `writeBar.refusedTypes` undecodable, and the store then refuses every command that reads its policy with `ERR_STORE_CONFIG` (see the store policy section below).
- `arc` is in `MEMORY_TYPES` and absent from `WRITABLE_MEMORY_TYPES` by design, so an agent can't assert a synthesis the corpus hasn't earned. The runtime filter and the restated `WritableMemoryType` schema are two copies of one list, and `packages/contracts/tests/types.test.ts:44-55` asserts they agree on every type.
- `task` sits on one axis with the other nine values instead of in a parallel `kind` column, because overlapping type vocabularies made classification unanswerable in the predecessor system (`packages/contracts/src/types.ts:11-16`). Tasks are excluded from search by filters that read this one column, so a second axis would mean finding and changing every one of them.

### Blast-radius notes

- The hash covers only `<article>` text, so head edits can't change it. ### Blast-radius notes

- This is the surface that reaches installed hosts. `hostSpec` resolves `root` to `$HOME` at user scope and to the git top level at project scope (`packages/integrations/src/hosts.ts:155-160`). Adding a host adds a branch there and a new set of files in someone's home directory (`packages/integrations/src/hosts.ts:168-175`, `packages/integrations/src/hosts.ts:196-260`), and `detectHosts` decides which hosts a bare install touches by probing `DETECT_DIRS` under the home directory (`packages/integrations/src/hosts.ts:271-277`). `apps/cli/src/integrations.ts:88` is where the user-scope root becomes `homedir()`.
- This radius has a stated recovery story. Only the receipt licenses a delete (`packages/integrations/src/receipt.ts:1-13`). Install refuses with `IntegrationModified` and writes nothing when a receipt-owned file has changed, and `--force` keeps a timestamped backup (`packages/integrations/src/install.ts:16-21`, `packages/integrations/src/install.ts:661`). Every write is atomic and every target is snapshotted first, so a failed install restores the prior bytes (`packages/integrations/src/fs.ts:87`, `packages/integrations/src/fs.ts:103-133`). A project install refuses the home directory and the filesystem root as its root (`packages/integrations/src/install.ts:648-659`), and no path with a symlink component is written (`packages/integrations/src/fs.ts:163`). A change that bypasses any of these steps removes a guarantee an operator's home directory has today.
- The hook engine's restatement is the `likely` row. `INDEXING_EVENTS` names `pre-compact` and `session-end` (`apps/cli/src/hook.ts:71`), the dispatch is a per-event `switch` (`apps/cli/src/hook.ts:303-309`), and `injects` asks `renderHookOutput` whether an event produces text (`apps/cli/src/hook.ts:222-223`). The type system checks the set's element type. It doesn't check which events belong in the set, so a fifth event added to `HOOK_EVENTS` compiles and then either indexes or doesn't depending on a line nobody was pointed at.
